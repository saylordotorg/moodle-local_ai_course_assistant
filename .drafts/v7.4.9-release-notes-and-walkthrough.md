# SOLA v7.4.9 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (17 September 2026)

**Retrieval stops re-reading the whole course index from the database on every single question, the Soapbox storage self-test stops reporting a working bucket as broken, and a reviewer gate stops passing pull requests it never reviewed.**

- **Retrieval is up to 21x faster on large courses.** Every question re-read and re-decoded the entire course vector index from the database, because the only cache was a PHP static that lived for one page load. Measured on a 2,020-chunk course at 2048 dimensions, that read cost about 4,380 ms while actually scoring the vectors cost 71 ms: the scan was never the expensive part. The index is now cached across requests as packed bytes, taking warm retrieval from about 4,609 ms to about 217 ms.
  - Caching the *decoded* vectors, which is the obvious approach, measured **slower than the database read it replaces** (3,580 ms to serialize, 117 MB). The packed form serializes in 6 ms at 16 MB. That measurement is why the code looks the way it does.
- **A reindex on one web server is now seen by the others.** The old cache was per-process, so reindexing a course on one node left every other node scoring against vectors that no longer existed until its PHP worker recycled. Invalidation now runs through a durable per-course generation counter that every node reads.
- **Three write paths that deleted or rewrote chunks never invalidated the cache.** Deleting a course (`observer::course_deleted`), re-indexing the site FAQ, and the `embedding_bin` backfill CLI all left stale entries behind. Harmless when the cache lasted one request; with a persistent cache, deleting a course and having its id reused would have served the new course the deleted one's content.
- **The Soapbox storage self-test could never pass.** Two independent bugs: `curl::put()` streams its body from a file on disk and silently issues no request at all when handed an inline string, so the upload reported HTTP 0; and the probe wrote to a path outside the configured recording prefix, which a correctly-scoped bucket policy is right to refuse with a 403. It now stages the body in the per-request temp directory and probes inside the recording prefix, so it exercises the same path a learner recording does.
- **`claude-review` can no longer report success without reviewing anything.** It had done so six times, and on one occasion that lost a real defect which then reached `main`. The cause was never permissions: `/code-review` launches its reviewers as background agents and the session was ending while they still ran. The job now fails when agents are abandoned, and the session is instructed not to finish while they are working.

### Known gaps, recorded deliberately

- The cross-node invalidation guarantee assumes a **shared** application cache store. The default file store in shared moodledata qualifies; APCu does not, and on such a site the 24-hour TTL would make per-node staleness worse than the old per-request static rather than better. Recorded in `db/caches.php` rather than enforced.
- Cache stores cap item size well below our own 64 MB ceiling (memcached at 1 MB by default). A rejected write is reported via `debugging()` rather than silently costing every request the full read.
- `int8` quantization would cut the remaining ~210 ms decode fourfold, and binary would cut it by 32. Neither was taken: int8 needs a full reindex (48.1M tokens on Degrees the first time) and binary changes retrieval quality and needs its own evaluation. Not worth it while the warm path is 217 ms.

### Testing

- Full PHPUnit suite: **1659 tests, 7273 assertions, 1 skipped, 0 failures**.
- Static validator suite: **36 passed, 0 failed, 0 skipped**.
- PHP lint clean on every modified file.
- CI: full matrix green (PHP 8.1/8.2/8.3 x Moodle 4.5/5.0/5.1 x pgsql/mariadb). The pgsql jobs matter here because the local suite is MySQL-only.
- 15 tests cover the new cache: pack/hydrate round trip for float, int8, binary and legacy JSON-only rows, a mixed float/int8 course, per-course and site-wide invalidation, the FAQ path, a corrupt cached entry that must be rebuilt rather than mis-sliced, and generation uniqueness across repeated flushes and a full cache purge.
- The review gate was verified against four real execution records rather than synthetic ones, including the run that had gone green while abandoning three of six agents.
- Jailbreak suite: see the run recorded at release time. Gate is 0 FAIL and 0 ERROR, not a pass rate.

## Part 3: Admin Walkthrough

### 1. Finish a quiz and immediately ask a question

Start an attempt on a quiz in a course, confirm the drawer is disabled and shows
the integrity notice, submit the attempt, then send a message in the same course.

**Expected:** it answers immediately. The lock lifts on submission, not when a
freshness window expires. Before this release it would keep refusing — and would
also refuse in every other course you opened.

### 2. Confirm the lock does not follow you between courses

With an attempt open in course A, open the assistant in course B.

**Expected:** course B works normally. Only course A is locked. If you want the
old site-wide behavior, Site administration → AI Course Assistant → *How far the
lock reaches* → **Every course**.

Worth knowing why the default changed: an abandoned attempt stays `inprogress`
forever, so under site-wide scope one forgotten quiz anywhere in a learner's
history disables the assistant in all their courses permanently.

### 3. Check that the input is disabled exactly when the server will refuse

While an attempt is open, open the drawer in that course.

**Expected:** the textarea and all six starter chips are disabled, and the notice
names the remedy — submit or close the attempt. There should be no state where
the box looks usable and the send is then refused.

### 4. Reload a conversation that had a failed turn

Open a course conversation with history.

**Expected:** zero occurrences of `core\`, `exception`, or `moodle_` anywhere in
the transcript. Old rows stored before 7.2.4 render the same learner-facing
notice as new ones.

### 5. Analytics with All courses selected

Site administration → Analytics, picker on **All courses**.

**Expected:** TOTAL ENROLLED carries a real number, at least as large as any
single course and at least as large as ACTIVE AI USERS. The two measure
different things: TOTAL ENROLLED is active enrollments, ACTIVE AI USERS is
people who actually used SOLA, so the gap between them is your adoption rate.
MSGS / ACTIVE USER divides by the second of those, not the first — which is why
both tiles were renamed in this release.

### 6. Read the privacy notice next to the audit log

Open the learner privacy notice, then the admin audit log.

**Expected:** the notice says SOLA keeps no record of its own of your name, and
that a name shown alongside SOLA data comes from your existing Moodle account.
That should read as consistent with the audit log showing full names.
