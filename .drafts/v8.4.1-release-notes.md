# SOLA v8.4.1: Release Notes and Short Walkthrough

DRAFT, not released. Written 26 November 2026 on branch `sola-841-marketplace-fixes`, build 2026112610. Nothing here has been checked on a live site or on the dev fleet yet: see "Not verified" below.

## Part 1: Release Notes

## v8.4.1: the plugin directory review fixes for 8.4.0

**Why this release exists.** The Moodle plugin directory reviewer recommended 8.4.0 for approval and listed five things to fix in a later release. 8.4.1 fixes all five. There is one data change on upgrade (the answer audit is re-sealed, item 1) and one visible change on sites that are not Saylor's (Saylor's names and links go away, item 2).

### What changed

**1. Erasure now unlinks the answer audit from the learner.** In 8.4.0, erasing a learner removed the question, answer and claim text from their answer audit rows but kept their user id, and the message and conversation ids, because the per-course hash chain covered those ids. Now:
- Each row carries a random salt (`linksalt`) and `linkhash` = SHA-256 of the salt, the user id, the message id and the conversation id. The chain (`rowhash`) covers `linkhash`, not the raw ids.
- While a row is live, the chain check recomputes `linkhash` from the salt and the ids, so moving a row to another learner, message or conversation is still detected.
- Every redaction (privacy erasure, course deletion, a cleared conversation, the conversation cap, retention) now also unlinks the row: the user id becomes 0, the message and conversation ids are cleared and the salt is deleted. `linkhash` stays, and without the salt it can't be tied back to anyone. The chain still verifies. A redacted row with an id or a salt put back fails the check.
- A verdict written for an answer that was already unlinked is written unlinked too.
- The teacher's note on a claim or rule review item is cleared when its answer is unlinked (the outcome and who resolved it stay), because a note can quote or name the learner.
- The audit page, its CSV and JSON export and the review queue show "Removed" as the learner of an unlinked row. The export never includes the salt. A learner's privacy export no longer includes rows already unlinked, since they are no longer linked to that learner.
- **Upgrade (step 2026112610): the chain is re-sealed once.** The step adds the two columns, then for each course it first checks the chain as 8.4.0 wrote it, then gives every row a salt and `linkhash` and rewrites every `prevhash` and `rowhash`. Rows that were already redacted under 8.4.0 are unlinked at the same time (8.4.0 kept the user id on them). Each course writes one `answer_audit_resealed` row to the audit log with the row counts and whether the old chain verified before the re-seal, and the upgrade prints one line per course. **A re-seal rewrites every hash, so the chain cannot prove anything about edits made before the upgrade except what that one logged check says.** If the log says the old chain was broken, the re-seal does not repair the evidence; it only records where it broke. A course with no 8.4.0 rows is never rewritten, and running the step again rewrites nothing.
- Known limits: an unlinked row keeps its course, activity, mode, model and time. On their own those name no one, but someone who also holds other logs of the same moment could match them up. The chain still has no secret key (unchanged from 8.4.0): someone with write access to the database can change a row and recompute every hash after it.

**2. Saylor's values are no longer other sites' defaults.** Until 8.4.0 the assistant name ("Saylor Online Learning Assistant"), the institution names ("Saylor University", "Saylor"), the contact and DPO email, the privacy policy link, the transcript URL pattern (`resources.saylor.org`), the footer courses link and one line of the external resources allowlist all defaulted to Saylor's values, and the code fell back to them when a setting was blank. Now:
- A blank assistant name shows a generic name ("AI Learning Assistant"), blank institution names show this site's full and short names, a blank contact or DPO email shows the site support email, a blank privacy link shows the site policy page when the site has one, a blank transcript pattern pairs no transcripts (as its help text always said), and the footer courses link ships hidden.
- Prompts and emails that said "Saylor" now use the configured institution name (insights, milestone emails, the objectives import). The benchmark's fixed system prompt no longer names Saylor, so its prompt fingerprint changes. The cost anomaly email now links to the site's own one-click unsubscribe page instead of a Saylor help page.
- **Upgrade, on sites that are not Saylor's:** a setting that still holds exactly the old Saylor default is replaced with the neutral one. Any other value was chosen and is kept.
- **Upgrade, on Saylor's own sites** (the host is saylor.org or sylr.org, or a subdomain: learn.saylor.org, degrees.saylor.org, dev.sylr.org, alpha.sylr.org): a setting never set, or blank where blank used to mean the Saylor value, is written with the old Saylor value, so nothing visibly changes there. A fresh install on a Saylor host does the same.
- **Which hosts count as Saylor's.** Only the site address (`$CFG->wwwroot`) decides: its host must be exactly `saylor.org` or `sylr.org`, or end in `.saylor.org` or `.sylr.org`. Nothing else is checked.
- **A staging or test clone of a Saylor site on another hostname** (for example a Catalyst staging address or `localhost`) is treated as any other site: on upgrade, settings that still hold the exact old Saylor defaults (institution names, assistant name, footer courses link, allowlist) are replaced with the neutral ones, and blank contact, DPO, privacy link and transcript pattern settings now fall back to that clone's own values instead of Saylor's. To get the Saylor values back on such a clone, set them under Essentials, Branding (Institution name "Saylor University", short name "Saylor", assistant name "Saylor Online Learning Assistant", contact email contact@saylor.org, DPO email dpo@saylor.org, privacy link https://www.saylor.org/privacypolicy/), the footer courses link ("Explore open online courses at saylor.org", https://www.saylor.org), the transcript URL pattern (`resources\.saylor\.org/transcripts/[^"'\s>]+`) and the allowlist line "Saylor Academy (learn.saylor.org)", or copy the plugin config from production. The exact values are in `classes/site_defaults.php` (`SAYLOR_VALUES`).
- **SOLA stays the default short name** on every site. It is the product's name, not Saylor branding, so it was kept on purpose; a site can change it under Essentials, Branding.
- Saylor attribution in LICENSE, README, CREDITS and the copyright headers is unchanged.

**3. More interface text moved into language strings.** About 100 hard-coded English messages now come from language strings (84 new keys, a dozen existing keys reused): the two review queue summaries, the inactivity reminder email, voice and microphone errors in voice.js and chat.js, chat notices, the voice panel status lines, the quiz difficulty and progress labels, the audio player labels, the stream errors chat.js used to show raw, the analytics tab headings and insights error, and the Learning Radar alerts, prompts and confirms. Learner and teacher strings are translated into the 45 other languages (machine-assisted, not reviewed by native speakers; Bambara and Wolof hold the English text for long sentences). The 17 Learning Radar admin strings are English only for now, and the five reworded branding and contact setting descriptions lost their old translations and show English.
- **Not moved in this release** (listed so nobody thinks it was done): the widget's settings panel, avatar picker, welcome card, feedback, survey and usability-testing panels, saved responses and message action labels built in `ui.js` (about 150 lines; that file has no string loader yet); the chat suggestion chips and the Review and Practice and My Progress panels in `chat.js`, some of whose logic matches the English text; the teacher-only context debug panel; the weekly digest, Learning Radar delivery and Zendesk emails; the cost anomaly email body; the default survey questions (stored content); and about 80 admin diagnostic messages (health check, integrity checker, backend probe, benchmark pages).

**4. No stray file in the package.** `README.md-E` (the backup a BSD `sed -i -E` writes) is removed. No other editor or tool artifact is tracked. The zip script excludes `*-E`, `*.orig`, `*.rej`, `*.bak`, `*~` and `*.swp` and stops if the zip lists any of them, and a test fails if one is in the plugin tree.

**5. One stated Moodle range.** version.php declares support for Moodle 4.5 to 5.3; CI covers 4.5, 5.0, 5.1 and 5.3 (5.2 is declared but not tested). The README's Requires line and Moodle Workplace section (which still said 4.5, 5.0 and 5.1), the version.php comment and the Marketplace description draft (`.drafts/marketplace-description-v8.4.1.txt`; the v7.8.0 draft still said "declared through Moodle 5.2" in its requirements) now all say that, and a test reads the CI matrix and version.php and checks all four places.

### Upgrade notes

- Schema: two nullable columns on `local_ai_course_assistant_answer_audit` (`linksalt`, `linkhash`). No other table changes.
- The re-seal reads and rewrites every answer audit row once, course by course, under the course lock. On a large audit this adds time to the upgrade.
- Rolling back to 8.4.0 means restoring the database from before the upgrade: 8.4.0 can't verify a re-sealed chain.

## Part 2: Short Walkthrough (about 3 minutes)

1. **Before upgrading**, note one course that has answer audit rows (Watch or Enforce on). Open its audit page and confirm the chain shows as verified.
2. **Upgrade** to build 2026112610. The upgrade prints one line per course: "answer audit chain re-sealed for course N (R rows, U unlinked; 8.4.0 chain verified before the re-seal)". Open Reports, then the SOLA audit log, and find the `answer_audit_resealed` rows; each says whether the old chain verified.
3. **Open the course's audit page again.** The chain still shows as verified. Rows whose text was already removed now show "Removed" as the learner.
4. **Erase a test learner** (Site administration, Users, Privacy and policies, Data requests, delete). Open the audit page: that learner's rows show "Removed", the chain still verifies, and other learners' rows are unchanged.
5. **On a site that is not Saylor's**, open Essentials, Branding: the institution and assistant name fields are empty, and the widget and privacy notice show this site's own name and support email. On a Saylor site, the same fields show the Saylor values as before.
6. **Switch the widget to another language** and trigger a voice error (deny the microphone): the message is in that language.
