# SOLA v7.0.1 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (20 August 2026)

Every language SOLA claims to support now actually carries the admin settings UI, and the Moodle Marketplace review of v7.0.0 is answered.

- **46/46 languages complete.** v7.0.0 made 86 admin settings translatable for the first time by pulling their titles and descriptions out of hardcoded English literals, shipping 170 new keys with 10 locales done. All 45 non-English locales now carry all 170, plus 6 keys for the new printable Learning Radar report — 7,650 strings. The staging scaffolding is deleted, so the parity test now guards those keys like every other one.
- **A CSS rule that was leaking to every page on the site is fixed.** v7.0.0 moved the settings-page table of contents styles into `styles.css` and brought a bare `html { scroll-behavior: smooth; }` along with it. Moodle aggregates plugin `styles.css` site-wide, so that rule applied everywhere, not just to our settings page. It is now scoped so it cannot match a page that is not already rendering our own table of contents.
- **Request-parameter validation tightened across the admin endpoints.** `PARAM_RAW` went from 40 uses to 19, and every survivor now carries a written justification for why raw input is required and where the strict cleaning happens. Three latent gaps turned up during the audit: the survey, usability-testing and objectives admin pages were decoding JSON envelopes and storing the fields with no cleaning at all, despite comments claiming otherwise.
- **CLI run artifacts moved out of the web-accessible plugin directory** into `dataroot`, replacing a bare `mkdir(0775)`. Three benchmark scripts were writing output into `dirroot`, which Moodle treats as read-only at runtime.
- **The last raw cURL handle is gone.** The RAG benchmark judge called `curl_init` directly, bypassing the site proxy configuration and the SSRF allowlist. It now uses Moodle's `\curl`. The plugin creates zero curl handles.
- **The printable Learning Radar report is a real Moodle page.** It used to emit a detached HTML document with an inline stylesheet and hardcoded English. It now renders through a Mustache template on an embedded page layout, so its styles live in `styles.css` and its text is translated into all 46 languages.
- **The demo seeder's clear path no longer loads every matching user into memory at once.** It pages with a forward-only id cursor. Worth knowing why: Moodle's `delete_user()` renames the account to `<email>.<timestamp>`, which still matches the `demo_student_%` pattern, so an offset-based loop would never terminate.
- Smaller review items: 14 CLI functions given frankenstyle prefixes, 17 camelCase variables renamed to the Moodle convention, `include(version.php)` replaced with the plugin-manager API, boilerplate headers added to four files, and 42 double-encoded mojibake sequences cleaned out of `chat.js` comments.

- **Three access-control bugs fixed** that the review pointed at but did not name. The talking-avatar viewer's ownership check was short-circuited by `$sid !== ''`, so omitting the parameter skipped verification entirely and rendered the stage for any logged-in user — it failed open. The personal-data page admitted the shared guest account, which every anonymous visitor on a guest-access site shares. And that same page passed an unvalidated `courseid` to `get_course()`, which ignores visibility, leaking hidden course names to any logged-in learner; the deletion itself was never exploitable because it was already scoped to the requesting user.
- **Two N+1 query fixes on hot paths.** Building the learning-objectives list runs on every course page view and went from 30 database reads to 1. Assembling the chat prompt went from 29 to 2. The instructor dashboard's mastery aggregate went from 191 to 5, and the outcomes report from 167 to 3. Because prompt assembly is involved, its output was pinned by checksum across both content orderings and a second set of truncation caps before and after.
- **88 more strings extracted** from the admin pages, including 22 English literals buried inside an inline `<script>` block, plus three more pages moved to Mustache templates with their inline styles namespaced.

Nine of the 26 findings the reviewer marked BLOCKER, and several HIGH ones, were checked against the code and found to be scanner false positives — interpolated SQL fragments that are literal `CASE` expressions with all user values already parameterized, and unsubscribe endpoints that are token-authenticated by design because RFC 8058 one-click unsubscribe has to work without a session. The reasoning is recorded in the changelog so the next review does not re-file them.

### Testing

- 809 tests, 3,492 assertions, 0 failures. (809 not 810: the v7.0.0 translation-batch guard was deliberately removed along with the exemption it guarded.)
- Validator suite 36 of 36.
- All 304 admin settings register, and every non-empty default plus every value currently stored on the dev fleet passes its own `validate()` after the parameter-type tightening.
- The language parity guard was confirmed to fail when a single translated key is removed, then restored — the test was falsified, not assumed.
- The flashcard reveal/grade flow was exercised end to end in a real browser. Its regression harness had been pointing at CSS classes the template migration renamed away, so it would have reported failure indefinitely without anyone noticing; it now targets the durable `data-*` hooks and passes.
- The jailbreak suite was not re-run. `context_builder::build_course_content` did change, but its output is pinned byte-for-byte by checksum across both orderings and two truncation-cap settings, and the learner `message` parameter is untouched — only the admin-gated model override changed. A jailbreak run would have re-tested an unchanged prompt.
- PHP lint clean on every modified file; `chat.min.js` rebuilt from source.
- Deployed and verified on dev.sylr.org, dev405.sylr.org, dev500.sylr.org (Moodle 5.0), and dev501.sylr.org (Moodle 5.1 with the `public/` layout).

Plugin version `2026082003`, release `7.0.1`.

## Part 3: Admin Walkthrough

Core drawer, quiz, voice, analytics, privacy, Soapbox and WSCUC-outcomes flows carry forward from v6.9.8. Two things are new.

### The settings page after the upgrade

Open Site administration → Plugins → Local plugins → AI Course Assistant → Settings on a site with default configuration. The feature toggles are all still there; their configuration is not, until you switch each feature on. Tick "Enable reranking" and its five fields appear inline.

If you had a feature configured before the upgrade, its settings are hidden but not lost — the values are still stored and reappear intact when you switch the feature back on. Nothing needs re-entering.

### Check your inactivity reminders

Worth two minutes on any site that runs learner email. Under Engagement, look at "Inactivity Reminders". If it is unchecked, this upgrade is the point at which that finally takes effect — those weekly emails were going out regardless before now. If you intended them to be off, nothing to do. If you find it unchecked and did want the emails, tick it.

### Rebranding

If you run SOLA under your own name, re-check the settings page after upgrading. Eight controls previously showed Saylor's branding regardless of what you had configured under Branding & UI; they now follow your `institution_name`, `institution_short_name`, `display_name` and `short_name`.
