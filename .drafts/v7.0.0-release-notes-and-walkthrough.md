# SOLA v7.0.0 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (20 August 2026)

A review of the global and per-course admin panels, asked for because the settings page had become hard to use. The review found more than clutter: three controls that were registered but never read, one of them a learner-facing email switch that had been ignoring its own off position.

Major version for one reason: a scheduled task that previously ignored its off switch now honours it, which changes observable behaviour on any site that had switched it off. Everything else here is visibility and cleanup.

### The inactivity-reminder switch actually works now (#190)

`inactivity_reminder_enabled` appeared in `settings.php` and nowhere else in the codebase. `send_inactivity_reminders` read only `inactivity_threshold_days`, so unchecking "Inactivity Reminders" in the admin UI did nothing at all and the weekly email kept going out.

The same task also lacked the plugin-`enabled` gate that its sibling `send_reminders` has always had:

```php
// send_reminders.php — has always had this
if (!get_config('local_ai_course_assistant', 'enabled')) { return; }

// send_inactivity_reminders.php — execute() went straight to the threshold
```

So on a site with SOLA switched off entirely, this task still emailed every learner holding a reminder row.

Both gates are now present. An unset value still reads as on, matching the setting's documented default of 1, so the fix cannot silently disable reminders on a site that upgraded before the config row was written — only an explicit "0" stops the send.

This is the same shape as the v5.13 `emergency_control --chat` no-op: a control that reads as working and isn't. Both were found the same way — by checking whether anything actually reads the setting.

### Three settings removed because nothing read them (#190)

**`failover_timeout_voice`.** Registered here and on the signed-policy-bundle allowlist, but no consumer anywhere; its `_chat` twin is read at `base_provider.php:507`. Its own help text admitted voice failover was never wired through. A remotely settable knob that does nothing is worse than a missing one.

**`talking_avatar_provider_url` and `talking_avatar_provider_api_key`.** Documented as a fallback so an admin upgrading mid-cycle would not have to re-enter a key. The fallback could not fire: `base_provider::cfg()` composes `'talking_avatar_' . $key`, and every caller passes a bare suffix (`api_key`, `base_url`, `persona_id`), so it looked up `talking_avatar_api_key` — a name that was never a registered setting. The API key field was therefore a credential prompt for a value nothing would ever read. The dead fallback branch is gone with them.

An upgrade step unsets all three so a stored credential does not linger in config for a field that no longer exists.

`tests/policy_bundle_test.php` gains a guard asserting every allowlisted key is still a registered setting. An orphan on that list is worse than a missing entry: `policy_bundle_tool --sign` accepts it, the bundle applies it, the audit row records a change, and nothing consumes the value. The guard was verified to fail when the orphan is reintroduced, not just to pass once it was removed.

### The settings page collapses to what you actually use (#190)

246 controls under 30 headings on a single `admin_settingpage`, every one rendered unconditionally. The file had grown a hand-rolled table of contents, jump anchors, smooth-scroll CSS and a floating Save link — scaffolding that exists only to survive the page's own length.

Moodle already solves this and the plugin used none of it: there were **zero** `hide_if()` calls. There are now 71, hiding detail behind the 22 toggles that own it, so a default install shows the feature switches and not their configuration.

Two rules kept this safe to apply mechanically:

1. Each setting depends on its **nearest** owning toggle, never a grandparent, so nothing carries two dependencies whose combination would decide its visibility. `rag_scorm_max_mb` hangs off `rag_extract_scorm`, which hangs off `rag_enabled`.
2. A toggle only owns settings it genuinely controls. The `embed_*` family sits under the "external resources" heading purely by position — `external_resources_enabled` governs whether the tutor may suggest outside links, nothing to do with embeddings — so those depend on `rag_enabled`. Gating them the way the layout implied would have hidden the embedding configuration behind an unrelated switch.

This is visibility only. Every hidden setting keeps its stored value, so switching a feature back on restores its configuration intact.

### The settings page rebrands completely (#190)

v6.8.0 white-labelled the product by tokenising every brand-bearing `get_string()` call. Settings whose title or description is a hardcoded PHP literal were never in scope, and eight of them kept showing Saylor's branding to an administrator at an institution that had rebranded. Two were worse than cosmetic:

- the voice-providers heading told every installer what "Saylor sites" must configure;
- per-call failover told admins to turn it on "once the chain has been validated and Saylor legal has confirmed FERPA addenda on each chain entry" — one institution's compliance process presented as product instruction.

All eight now resolve through `branding::apply()`, and those two sentences are generic. One lang string (`settings:provider_desc`) carried the literal twice and is now tokenised — and read via `branding::str()`, because a tokenised string read with a bare `get_string()` renders `[[tutorshort]]` to the admin, trading one leak for a worse one.

A new guard rebrands all four brand settings, rebuilds the real admin tree, and asserts that no setting renders the default brand or an unresolved token. Overriding only some of the four is how an earlier version of that check produced false positives, since `[[unishort]]` still resolved to the Saylor default.

### The settings page became translatable (#191)

86 settings and headings had their title and description written as hardcoded PHP literals rather than `get_string()` calls. The v6.8.0 white-labelling covered `get_string()` calls only, which is how eight of them kept showing Saylor's branding; but the underlying problem was larger — those strings were not translatable at all, and the 46/46 completeness check could not see them, because it measures whether every key in `lang/en` has a translation and these had never been keys.

All 86 are now extracted into 170 new lang keys and read through `get_string()`, or `branding::str()` where the string carries a brand token. Four headings that concatenated a `moodle_url` now pass the URL as a `{$a}` parameter instead of embedding it in the sentence.

The refactor was verified by capturing every setting's rendered title and description before and after, and diffing: **304 settings, 303 byte-identical**. The single intentional difference is `institution_name`, which now reads from a pre-existing translated lang key rather than its own literal.

Ten locales are translated: Spanish, French, German, Chinese (Simplified), Arabic, Portuguese (Brazil), Russian, Japanese, Hindi and Italian. Each was validated for preserved `{$a}` placeholders, preserved `[[brand]]` tokens and matching HTML tag structure — a diff of 1,700 strings does not show a dropped placeholder, and a missing one silently drops a URL out of a sentence.

### Read this before upgrading

**A site that switched inactivity reminders off has been sending them anyway.** After this upgrade that setting is obeyed and those emails stop. That is the fix working, but it is a change in observable behaviour for any site that had unchecked the box. A site that left it at the default sees no change.

Nothing else changes behaviour. The three removed settings had no readers, and the `hide_if` work changes visibility only.

### Known and not fixed

- **35 of the 46 language packs do not yet carry the 170 new settings keys.** The extraction below made those strings translatable; translating them is a separate batch. Moodle falls back to `lang/en` for a missing key, so those settings render in English on those locales — exactly as they did before this release, when the text was hardcoded. No regression, but the packs are no longer uniformly complete and the release notes should not claim otherwise.
- The settings page is still **one page**. Splitting it into the seven sections its own table of contents already names would retire the TOC, the seven anchor pseudo-settings, and the inline `<style>` block that re-introduced a CONTRIB-10574 reviewer finding. Deliberately left for its own release.
- Several settings still render under an unrelated heading, because headings are positional: "Spend alert recipients" sits under "Signed policy bundles". The page split fixes this class by construction.
- **The per-course panel** (`course_settings.php`) was reviewed and nothing was deprecated: 15 fields, already grouped into cards with a description per card and help text under every field. Two things were noted and left. Its three newest cards — English Lock, Voice Tab, Auto-open — are entirely hardcoded English (20 text nodes), two of them naming SOLA literally, so they sit outside white-labelling the same way the settings-page literals did. And those three are structurally identical three-way overrides (Inherit / Force on / Force off) that would collapse cleanly into a single "Per-course overrides" card, taking the panel from six cards to four.
- Failover remains **unverified in practice**.

## Part 3: Admin Walkthrough

Core drawer, quiz, voice, analytics, privacy, Soapbox and WSCUC-outcomes flows carry forward from v6.9.8. Two things are new.

### The settings page after the upgrade

Open Site administration → Plugins → Local plugins → AI Course Assistant → Settings on a site with default configuration. The feature toggles are all still there; their configuration is not, until you switch each feature on. Tick "Enable reranking" and its five fields appear inline.

If you had a feature configured before the upgrade, its settings are hidden but not lost — the values are still stored and reappear intact when you switch the feature back on. Nothing needs re-entering.

### Check your inactivity reminders

Worth two minutes on any site that runs learner email. Under Engagement, look at "Inactivity Reminders". If it is unchecked, this upgrade is the point at which that finally takes effect — those weekly emails were going out regardless before now. If you intended them to be off, nothing to do. If you find it unchecked and did want the emails, tick it.

### Rebranding

If you run SOLA under your own name, re-check the settings page after upgrading. Eight controls previously showed Saylor's branding regardless of what you had configured under Branding & UI; they now follow your `institution_name`, `institution_short_name`, `display_name` and `short_name`.
