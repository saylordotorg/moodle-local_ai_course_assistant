# SOLA v7.5.3: Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (24 September 2026)

**Learners can be shown where they stand on their degree program's outcomes, not just on the course in front of them, and the plugin now proves in CI several things it had only been asserting in comments.**

- **A "Your program outcomes" panel, for learners, in the progress panel.** It reads a learner's program-level outcome attainment from the Outcome Map plugin (`local_outcomemap`) and shows it beside SOLA's own course-level mastery, without merging the two. They answer different questions. SOLA's mastery asks whether this learner has mastered the objectives of this course, from attempts SOLA itself recorded. Outcome Map asks where the learner stands on the program's outcomes, pooled across every course that contributes released evidence, from graded questions a human mapped to an outcome and approved. The second is evidence a course-scoped tool cannot produce, which is the entire reason to read it.
- **Every outcome without a result says why, in words.** Only a `calculated` state carries a percentage. When last measured, on the production degrees site on 2026-09-22, 525 of 546 result rows had no figure, so "no number" is the normal case rather than an edge. Each state gets its own short label where the percentage would be, and its own sentence below, because "nobody has assessed this yet" is not the same as "your result exists but has not been published". Nothing is ever rendered as zero, and no row is left blank, including the case where the source claims a result exists and supplies no number.
- **The panel appears only where it means something.** It renders only if the learner has attainment in a program the course they are looking at actually contributes to. A panel on a course with no outcome mapping is an empty box asking a learner to care about something their course does not take part in, and a panel with no rows is worse: it implies the reader has been measured and found empty. The narrowing happens inside Outcome Map, where the program-to-course mapping and its effective dates live, rather than in SOLA reimplementing them.
- **It could not have worked for a learner, and that is fixed upstream rather than worked around.** The only way to read pooled program attainment from Outcome Map was its SIS export function, which takes an arbitrary user id and therefore requires a site-level capability. No student holds it, and granting it to one would let that student read anybody's attainment. Verified against a real learner on dev. So the missing piece was a learner-safe API, and it is now proposed upstream as dta121/moodle-local_outcomemap#9: a function that takes no user id at all and can only ever answer about its caller. SOLA is built against it and falls back to showing nothing without it.
- **The panel is all-or-nothing per site, deliberately.** It is gated on that learner-safe function specifically, not on "attainment is readable at all". Without that line, a site running an older Outcome Map would show the panel to administrators and to nobody else, so the only people able to check whether the feature worked would be the only people it worked for. Absence gets noticed; a staff-only panel does not.
- **Off by default, with one switch.** `outcomes_panel_enabled`. Turning it on should be a deliberate act by somebody who then looks at the result, not something that happens by itself the day an unrelated plugin is upgraded.
- **A latent failure in how the plugin called another plugin.** The bridge used `external_api::call_external_function()`, which is the HTTP and AJAX entry path and calls `require_sesskey()` for any login-required function outside a web service server. Whether it worked therefore depended on whether the surrounding request happened to carry a sesskey, which the AJAX progress call does and cron, CLI and a plain page render do not, with the failure swallowed into a debug line either way. It now resolves the function through the external-services registry and calls the implementation directly. One thing is given up and it is worth naming: the wrapper also runs `clean_returnvalue()`, and that throws on a shape it does not expect, so keeping it would mean the panel disappearing the day a third-party plugin adds a field. Degrading to a missing value beats degrading to a missing panel. The checks that matter are not given up, because the capability and context checks live inside the function itself.
- **Every endpoint that skips `require_login()` now declares it the same way.** Three sessionless endpoints authenticated by a token or bearer key carried the intent only through `NO_MOODLE_COOKIES`; three others carried it through a phpcs suppression. Two conventions meant two descriptions of the same code, and we gave the Moodle plugin-directory reviewer the wrong one twice. All six now carry the same marker with a comment saying what authenticates the caller instead, and a test pins both that and the cookie map by value rather than by presence, which was the specific mistake.
- **The packaged README names the release being packaged.** A direct recommendation from the plugin-directory review, fixed once and drifted again by four releases. A test now fails the build if `README.md` and `version.php` disagree.
- **i18n: 33,588 strings into all 45 locales, and the lists that tracked the gap now tell the truth.** Three separate failures were hiding behind one green check. 401 keys were simply missing. 339 more were present in every locale holding the English text verbatim, which passes every automated check and reports full parity while a reader sees English; 68 of those are the privacy declarations Moodle shows a learner who asks what this plugin stores about them. A final 63 were on a debt fixture nobody had pruned. The worst of it was teacher-facing: the per-course settings page is reachable by any editing teacher, and the course instructor dashboard is reachable by any teacher, and both were English throughout. Every translation is machine-checked for placeholder, branding-token, HTML and `<code>` parity, and each locale is scanned for expected-script coverage and for values that came back identical to the English.

- **Several things this plugin asserted in comments are now checked by tests.** A claim about how Moodle's external API handles an undeclared return key was repeated in five places, including a commit message and an account of a production outage that never happened; it was wrong, and the outage did not occur. The map of which endpoints suppress session cookies was stated to a plugin-directory reviewer twice and got wrong twice, by counting the presence of a declaration rather than its value. Production row counts were quoted as current fact in five comments. All of it is now either pinned by a test or carries the date it was measured.
- **Accessibility and cost, both found by an adversarial pass and both measured rather than argued.** The panel dimmed with `opacity` while the progress panel around it uses explicit greys, which makes contrast depend on whatever is behind the text and, in Windows forced-colors mode, dims text the operating system has just set to maximum contrast on purpose. It now uses greys at 4.8:1 and 7.5:1 on white, with the explanation a learner most needs to read being the more legible of the two. The section is no longer a third `aria-live` region re-announcing the whole list on every render, and the outcome list keeps its list semantics in Safari with VoiceOver. Reading the panel measured 22 queries and about 8ms per contributing course, which is linear in a learner's result history, so it now goes through a five-minute cache; the kill switch is still read first.

## Part 2: Key SOLA Features

Carried forward from v7.5.2. One new capability: the learner-facing **Your program
outcomes** panel (`outcomes_panel_enabled`, off by default), which reads program-level
attainment from the Outcome Map plugin and requires Outcome Map 0.9.4 or later. No other
feature changes. Soapbox remains deprecated, unchanged, and scheduled for code removal in
v8.0.0.

## Part 3: Admin Walkthrough

The order matters here. Steps 1 and 2 are the ones every site can run, including one
without Outcome Map, and they are the ones that prove the release is safe to have on.
Steps 3 onward need Outcome Map 0.9.4 and a learner with real attainment.

### 1. Confirm the default is silence

Go to Site administration, Plugins, Local plugins, AI Course Assistant. Find "Show
learners their program outcomes". It is unticked.

Open a course as a learner and open the assistant. Go to the Progress tab. You see the
usual mastery panel and nothing else. That is the whole of the change for a site that
does not use Outcome Map, and it is what every Saylor site will see on the day this is
deployed.

### 2. Tick it, and confirm nothing happens yet

Tick the setting and save. Purge caches. Reload the learner view.

Still nothing. That is correct, not a fault. The panel needs Outcome Map 0.9.4, which
exposes a function that can report a learner their own attainment. Without it the only
route to that data needs a site-level capability no student has, so the panel refuses to
render for anyone rather than rendering for administrators only. Untick it again if you
are not ready.

Worth understanding rather than skipping: a panel that appears for staff and never for
the learners it describes is the worst outcome available, because the people checking
whether it works are the only people it works for.

### 3. With Outcome Map 0.9.4: a course that uses outcomes

Pick a course that belongs to a program in Outcome Map and a learner with at least one
released result. Open the assistant as that learner, Progress tab.

Under the mastery panel there is now a "Your program outcomes" section, one block per
program, one row per outcome.

### 4. Read a row that has no number, which is most of them

Most rows will have no percentage. Each one says why in a sentence, and the sentences
differ: not enough evidence has been collected yet, a calculation is queued, the figure
is out of date, the result is calculated but not released, the outcome is not assessed in
this program.

Check that none of them shows 0%, an empty cell, or a bar drawn at zero width. On the
production degrees site, 525 of 546 result rows have no number, so this is the normal
view rather than an edge case. A learner reading a wall of zeroes would conclude they had
failed outcomes nobody has measured.

### 5. Confirm the panel is absent on a course that does not use outcomes

Same learner, a course that belongs to no program. The section is gone entirely, not
present and empty. The learner still has program results; they are just not relevant to
the course they are looking at.

### 6. Confirm it is the learner's own data and only theirs

Log in as a teacher on the same course and open the assistant. The teacher sees their own
progress panel, not the learner's. There is no path in this feature that shows one
person's attainment to another: the function it calls takes no user id at all, so there
is no request it can be made to answer about somebody else.

### 7. Turn it off and confirm it goes away

Untick the setting, save, purge caches, reload. The section is gone on the next page
load, with no deploy. That is the intended way out if it behaves badly, and it is the
reason the setting exists at all in a release that ships just before a long quiet period.
