# SOLA v7.2.4 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (29 August 2026)

### The panel that answers "is anyone using this" reported zero

A verification pass over 7.2.3 confirmed all eight of its claimed fixes and left
one finding open: on a dev site carrying real traffic, the Overall Usage panel
showed zero students, zero sessions and zero messages. Chasing that properly
turned up a larger version of the same bug, and this release closes it along with
the tail of the 7.2.3 review.

- **Site-wide analytics counted nothing.** Course id 0 means "every course"
  throughout the dashboard — it is what the All courses option sends. Six
  counters never implemented it: `get_overview()` and five siblings interpolated
  `WHERE courseid = :courseid` unconditionally, so a site-wide request became a
  filter for rows literally stored against course 0, of which there are none.
  Each was correct per-course, which is why this survived — the panel is only
  wrong in the one mode that has no course page to check it against. All six now
  route through a single `course_clause()` helper, and a test writes activity
  into two real courses and asserts the site-wide call sees both.

- **The prompt budget now comes from the model, not from a measurement.** A fixed
  character budget has been wrong twice: 12,000 could not hold the prompt at all,
  and 24,000 cleared a live BUS101 turn by 46 characters. Both were set by
  measuring one configuration and assuming it generalized. SOLA now reads the
  configured model's context window, subtracts the reserved reply and the
  conversation history, and uses the larger of that and the configured budget —
  so the setting is a floor, never a ceiling the model argues down. A model that
  is not in the lookup table moves nothing, and a self-hosted
  `backend_context_tokens` still wins outright. It is a ceiling, not a target: it
  only fills if retrieval has that much to put in it, so the measured
  27,991-character turn costs exactly what it did before.

- **Ten credentials were sitting in the clear in the config change log.** The
  review found one, in a different plugin, by grepping the page for a key it
  already suspected. Auditing the table properly found ten on that site and
  sixteen across the dev fleet, in five plugins including this one and Moodle
  core — all readable at `/report/configlog` by anyone who can reach site
  administration. Registering a setting as a password type masks it in the
  settings form and does nothing for a value written by a CLI script, an install
  step, or an upgrade step. New: `admin/cli/audit_config_log_secrets.php`
  reports them site-wide and can overwrite the values while keeping the rows.
  It never prints a key.

- **Course deletion now takes SOLA's data with it.** A `course_deleted` observer
  clears the 23 course-scoped tables and the per-course setting overrides. The
  audit log and email opt-outs are deliberately preserved.

- **Ten course-scoped tables were silently absent from course backups**, among
  them surveys, unit-task responses, objective links, learner profiles and
  learner memory. They are in the archive now, along with course-level plugin
  settings — and those restore into merged and imported courses as well as new
  ones, because `restore_course_task` only builds the course-level step for a new
  course, so the payload now also rides on the section task.

- **A failed turn no longer discards what the learner typed.** The message stays
  in the box with a short, non-blaming notice.

- `tests/golden` is excluded from the published zip.

- The code-review workflow's tool grant now covers the read-only shell utilities
  its subagents pipe `gh` output through, and `show_full_output` is on so the
  next denial names itself instead of being guessed at a sixth time.

### Upgrade notes

No schema change, no upgrade step. `prompt_budget_mode` defaults to Derive from
the model; existing sites pick that up automatically and their configured budget
becomes the floor, so no site's prompt gets smaller. Set it to Fixed to keep the
old behaviour exactly.

Run `php local/ai_course_assistant/admin/cli/audit_config_log_secrets.php` once
after upgrading. It is site-wide, not scoped to this plugin, and on the dev fleet
it found exposed keys in four other plugins.

### Testing

## Part 3: Admin Walkthrough

### 1. Ask a course question from a course page

Open a course with retrieval on and an index built, navigate to a page inside it,
and ask something answerable only from the course text.

**Expected:** the answer quotes the course. Grounding renders as a chip beneath
the reply naming the source activity — *From: Forms of Business Ownership* — not
as inline `[[c:N]]` markers. Those markers are the model's internal citation
protocol; the renderer converts them and they should never be visible. A literal
`[[c:N]]` in an answer is a bug.

### 2. Check the analytics overview with All courses selected

Site administration → Analytics, course picker on **All courses**.

**Expected:** Total Students, Active AI Users, Total Sessions, Msgs/Student and
Return Rate all carry real numbers. Before this release every one of them read
zero site-wide while the same figures were correct on any individual course —
that mismatch is exactly what this release fixes. Pick one busy course and check
its numbers are no larger than the site-wide ones.

Note the Total tokens tile counts every AI call including retrieval, so on a site
with RAG enabled it is dominated by embedding and reranking and will look very
large next to the chat session counts. Both are correct; they measure different
things.

### 3. Look at the system prompt budget mode

Site administration → AI Course Assistant, System prompt budget mode. Leave it on
**Derive from the model**. The character budget below it is now a floor: raising
it still raises the budget, lowering it no longer starves the prompt on a model
with room to spare.

If SOLA has recently had to cut retrieved course content to fit, a warning
appears above the budget with the time it last happened. On a healthy site you
should not see it.

### 4. Run the config-log secret audit

From the Moodle root:

```
php local/ai_course_assistant/admin/cli/audit_config_log_secrets.php
```

**Expected on a clean site:** *No credentials found in the clear in config_log.*

If it lists rows, each one is a live key readable by anyone who can reach
`/report/configlog`. Re-run with `--redact` to overwrite the values — the rows
survive, so the audit trail is intact — and then rotate those keys at the vendor.
Redaction is not rotation.

### 5. Test the emergency chat switch as a student

Disable chat, then open a course in a private window as a test student. You should
get a short paused notice. Check it as an administrator too — it stops you as
well, which is the point.

Then open the audit log: the pause is recorded as `chat_paused`, not as an error
row.

### 6. Delete a scratch course

Create a throwaway course, use the assistant in it once, then delete the course.
SOLA's conversation, message, profile and memory rows for that course go with it,
along with any per-course setting overrides. The audit log keeps its entries on
purpose — deleting a course should not erase the record that something happened.

### 7. Back up and restore a course that uses per-quiz assistance levels

Set a quiz to a restricted assistance level, back the course up, and restore it
**into an existing course** as well as into a new one. The level should travel in
both cases and should point at the restored copy's own quiz. Restoring into an
existing course did not carry course-level settings before this release.
