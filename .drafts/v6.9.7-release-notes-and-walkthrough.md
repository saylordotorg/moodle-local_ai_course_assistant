# SOLA v6.9.7 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (18 August 2026)

An incident release. No schema change, no migration. One new scheduled task, one new setting group.

### What happened

On 2026-08-10 an Anthropic organisation spend cap began rejecting every call for the ten courses routed to Claude on learn.saylor.org. Over the following nine days **140 learners asked 330 questions and received 9 answers** — a 97% failure rate. Every one of them saw "Sorry, something went wrong. Please try again."

Nothing alerted. Diagnosis eventually required a manual `curl` against the API, because the plugin was discarding the one piece of information that would have identified the cause immediately. The API had been returning it on every single call:

```
invalid_request_error: You have reached your specified API usage limits.
You will regain access on 2026-09-01 at 00:00 UTC.
```

This release makes that class of failure both visible and detectable.

### Read this before upgrading

Nothing here changes behaviour for a healthy site. Two settings groups are added, both **off by default**, and one bug fix changes what an already-broken site displays.

If you run more than one provider, the credential guard in `create_for_comparison()` is now stricter: requesting a provider that has no **Comparison providers** row and is not the site provider will be **refused** rather than silently sent another vendor's key. That refusal is the correct behaviour — the previous silent attempt could only ever fail — but if you have been relying on the old behaviour by accident, you will now see a clear error where you previously saw an opaque `HTTP 400:`.

### Errors now surface (#185)

Three places discarded the provider's own error, and the two that mattered are both on the **streaming** path the chat drawer uses:

- `chat_completion()` threw the fixed literal `Invalid API response`, binning the payload.
- `chat_completion_stream()` had **no branch for an SSE `error` event**, so a mid-stream failure produced an empty reply and no exception.
- The same method **skipped any line not starting with `data: `**, so a rejected request's plain JSON error body was never parsed at all. That is the shape a spend cap returns.

This is why the outage was invisible in chat while the **quiz kept working** — the quiz calls the non-streaming method on the same provider, key and course. That contrast is what finally localised the fault.

`sse.php` now records `moodle_exception::$debuginfo` as a `detail` field on the `sse_error` audit row. The next provider failure is diagnosable from the audit alone, without turning on debugging on a live site.

### One vendor's key no longer reaches another (#185)

`create_for_comparison()` inherits the course's effective config — including its API key — then looks up the requested provider in `comparison_providers` for the correct credential. When that lookup missed, it passed the inherited key through regardless.

An admin whose in-widget LLM picker was set to `gemini` on an Anthropic course therefore had that course's Anthropic key handed to a Gemini client, producing a bare `HTTP 400:` with no message. `KEYLESS_PROVIDERS` exempts `stub`, `ollama` and `coreai`, which legitimately run without a SOLA-managed key.

### Unanswered-question monitor (#186)

New scheduled task `unanswered_check`, every two hours. Alerts when a course above a minimum question count falls below a minimum answer rate.

Every existing monitor watches the wrong direction — `cost_anomaly_detector` fires when spend goes **up**, and a provider rejecting everything costs nothing. The question-to-answer ratio sits near 1:1 normally and drops to zero the moment a provider breaks.

Against the August outage, CS101 crossed the threshold within hours: **day one instead of day nine**.

### Active-learners indicator (#184)

- Fixed a line that rendered its own string id (`active_learners:line_global`) on every load. Moodle caches JS strings keyed by id/component/lang **without** the parameter, so a parameterised `Str.get_string()` can be served from cache and skip the server. `CLAUDE.md` already warned about this exact trap.
- New `active_learners_enabled` setting, **default off** — it is social proof rather than a teaching feature, and costs a poll every 60 seconds per open drawer.

### Testing

Three checks caught mistakes during this release, which is worth recording because each was a fix of mine that looked right:

1. The `soapbox_slide_vision` test caught a credential guard that would have broken **every keyless provider**.
2. The `health_check` test caught a **new scheduled task with no version bump**, which would have shipped silently unregistered — precisely the failure the monitor exists to prevent.
3. The i18n CJK-leak guard caught a stray Han character in a Ukrainian translation draft.

### Known and not fixed

- `base_provider`'s constructor treats an empty `apikey` override as *unset* and falls back to the site key, so there is no way to express "no credential" through overrides. Documented in code; unchanged here because it touches every provider construction path.
- Failover remains **unverified in practice**. `spend_failover_chain` and `failover_per_call_enabled` were configured on both production sites during this incident and never engaged, because the errors escaped before the decorator. Whether this release's changes make it work has not been tested.
- `provider_benchmark.php` still carries two hardcoded admin-only strings.

## Part 3: Admin Walkthrough

Core drawer, quiz, voice, analytics, privacy, Soapbox and WSCUC-outcomes flows carry forward from v6.9.6 / v6.8.32. Two things are new and worth five minutes each.

### Turning on the unanswered-question monitor

Site administration → Plugins → Local plugins → SOLA.

Set **Alert when questions go unanswered** to on. Check that **Spend notification emails** has a real recipient list — if it is empty the alert falls back to every site administrator, which is probably wider than you want.

The defaults are deliberately conservative: a 6-hour window, at least 5 questions before a course is judged, and a 0.5 answer rate. The rate is not set near zero on purpose — 0.5 catches a *partial* failure, such as one provider of several being down, which is the case most likely to go unnoticed.

To see what it would say without waiting for cron, run the task manually:

```
php admin/cli/scheduled_task.php --execute='\local_ai_course_assistant\task\unanswered_check'
```

It prints per-course asked/answered counts whether or not it alerts, so it doubles as a quick health readout.

### Reading a provider failure from the audit log

When a learner reports "something went wrong", look at the `sse_error` rows in the SOLA audit log. Since this release they carry a `detail` field with the provider's own message — the HTTP status, the vendor error type, and the text.

That distinction matters: a dead API key, an organisation spend cap, a retired model and a network timeout all produce the same learner-facing string, and before this release the audit recorded only that string. The `detail` field is what tells them apart.
