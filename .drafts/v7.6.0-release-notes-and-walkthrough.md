# SOLA v7.6.0: Release Notes

## Part 1: Release Notes (1 October 2026)

**The Moodle plugin-directory review: both approval blockers and six other findings.**

The reviewer filed fourteen issues against release 7.5.2. Eight are closed here. One of those was already fixed before he looked. Five of the remaining findings turned out to be wrong or incomplete as filed, which is recorded below because it changes what was done.

### Blocker: learner-facing AI behaviour came from a remote file

Every installation of this plugin fetched `sola-config.json` from the `main` branch of one GitHub repository, once an hour, and applied its `system_prompt`, `instruction_blocks` and `model_default` to the assistant its learners talk to. The setting shipped with that URL as its default and an empty value fell back to the same URL, so an administrator could not switch it off by clearing it.

Anyone able to write to that file could change what the assistant tells learners on every site running the plugin, including replacing the house-style rules that carry the self-harm and crisis guidance, and could change which model is billed. No plugin release, no code review, no administrator upgrade.

Remote configuration is now opt-in. The setting ships empty, empty means disabled, and `DEFAULT_URL` is an empty string with a comment explaining why it must stay that way.

Shipping an empty default only helps new installations, so there is an upgrade step. It clears the setting **only** where the stored value exactly matches the historic default, because a site carrying that value never chose it; a site that set its own URL made a deliberate choice and keeps it. It also purges the config cache, which would otherwise keep serving remote prompt text for up to an hour after the upgrade that disabled it.

### Blocker: the privacy provider did not find all learner data

Ten tables link a learner to a course and appeared in neither `get_contexts_for_userid()` nor `get_users_in_context()`: flashcards, obj_att, learner_goals, streak, learner_memory, profiles, struggle_signal, outreach_log, avatar_sess and email_optout.

A learner who had only used flashcards in a course was returned by neither method. A subject access request exported nothing of theirs and a deletion request left it in place.

The cause was structural rather than an oversight about any one table. Both methods carried one hand-written SQL block per table, so adding a table meant remembering to add two more blocks, and over several releases nobody did. Both now iterate a single list, and `tests/privacy_discovery_coverage_test.php` reads `db/install.xml` and fails when a table with a `userid` and a `courseid` is missing from it.

This was reported in June, fixed partially, and came back. The test is what stops a third round.

### Chart.js now comes from core

`cdn/chartjs/` held a 205 KB copy of Chart.js 4.4.7, loaded by three classic scripts: the library bracketed by a pair of guards that hid `window.define` across its load. The guards existed for a real reason, recorded in the code, which is that the UMD bundle prefers AMD when it sees a loader, Moodle always has RequireJS on the page, and the result was an anonymous module RequireJS rejected while `window.Chart` was never installed. Every canvas rendered empty while the headline numbers populated normally.

Moodle core already ships `core/chartjs`, and core consumes it the same way. Declaring it as an AMD dependency removes the problem rather than working around it. The bundled copy, both guard scripts and `thirdpartylibs.xml` are all deleted; Chart.js was that file's only entry, so the plugin now ships no third-party code at all.

### The rest

The single impure language-file assignment is one literal again. The course-deletion observer reads plugin settings through `get_config()` and removes them with `unset_config()` rather than querying `config_plugins`. The conversation-starter admin page carries its configuration in a data attribute instead of a `js_call_amd` argument, which Moodle warned about on every load. Three global constants in the CLI scripts now carry the Frankenstyle prefix.

### What the review got wrong, and why it matters

Each finding was checked against the code before being acted on. Five were wrong or incomplete.

The constant finding cited one `define()`; there are three, two of them file-scope `const` in a second script. All three are fixed.

The language-file finding described a class of problem; there is exactly one case, at line 1760 rather than the cited 1751. Finding it by grep is actively unsafe: searching for the concatenation pattern matches forty-plus valid strings in Swahili, Slovak and Polish where a quotation mark is followed by a sentence-ending period. It was found by tokenizing all 46 files instead.

The configuration-API finding suggested enumerating the per-course setting prefixes. There is no fixed list: several modules mint their own keys, so an enumeration would need updating whenever one is added. The suffix rule covers every present and future key.

The listing finding was two-thirds already fixed between 7.5.2 and now.

The Pyodide finding's "by default" framing is not accurate, though its substance holds, and it remains open.

### A gap worth more than the finding it hid

The reason the language-file defect reached a reviewer is that this repository's own drift test could not see it. `tests/i18n_translation_drift_test.php` parses with a regular expression requiring a semicolon immediately after the closing quote, so it silently dropped that key: 2,910 keys parsed against 2,938 defined. The string was invisible to CI, and so were 27 others. Fixing the parser is worth more than fixing the one string, and is tracked separately.

### Testing

1,937 tests, 0 failures, 7 skipped. Security validators 36 of 36. PHP lint clean across 586 files. Both rebuilt JavaScript bundles verified against their sources, which matters here because a stale `analytics_dashboard.min.js` would still expect a global `Chart` and silently render every canvas empty.

Plugin version `2026100100`, release `7.6.0`.

## Part 3: Admin Walkthrough

Unchanged from v7.5.7, with one addition: after upgrading, check Site administration, Plugins, Local plugins, AI Course Assistant, and confirm "Remote config URL" is empty. If your site had never set it, the upgrade has cleared it and remote configuration is now off. If you had set your own URL, it is untouched and still active.
