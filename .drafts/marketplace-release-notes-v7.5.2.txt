Version 7.5.2 (build 2026091900)

Soapbox, the spoken-presentation feature, is deprecated in this release and will move to a plugin of its own. Everything it stores now behaves the way it says it does.

DEPRECATED: SOAPBOX

Soapbox is deprecated. It keeps working exactly as it does today, nothing is deleted, and no setting changes. What stops is development.

It is moving into PresenterAI, a separate Moodle activity plugin that does the same job, appears in the activity chooser, and adds two things Soapbox never had: a choice between an S3-compatible bucket and Moodle's own file storage, with automatic deletion becoming optional rather than fixed, and a choice between Moodle core's AI subsystem and Claude, OpenAI or Gemini configured directly.

The reason is structural rather than a judgement about the feature. A presentation activity inside a chat assistant cannot appear in the activity chooser, cannot be graded like an activity, and forces every site that wants presentations to install a whole learning assistant to get one.

The code is scheduled for removal in v8.0.0. The database tables are removed separately and later. That split matters: Soapbox writes no gradebook entry, so a learner's transcript, score and written feedback exist in three plugin tables and nowhere else in Moodle. Removing the code destroys nothing. Dropping the tables destroys the only copy. No release will remove Soapbox until PresenterAI can import existing recordings and scores.

Administrators see a notice on the settings page, and only if the site actually has Soapbox switched on somewhere. Teaching staff see one on the assignment page. Learners see nothing, because nothing changes for them in this release.

UPGRADE NOTES

No action is required. No data is touched, no setting changes, and no table is added, altered or dropped. If you run Soapbox, stop building new courses on it; everything already built keeps working.

FIXED: WHAT SOAPBOX STORED

Three things it stored did not behave the way the product said they did. None of them required a site to have done anything wrong.

A description of a learner's body outlived the video it described. The body-language feature added in 7.5.1 samples six stills from a recording and deletes them with the video on the retention clock. It kept the text the vision model wrote about them, because that sits on the score row and score rows deliberately survive retention so learners keep their feedback. So a description of where a named learner's hands were was retained indefinitely, in a field nothing in the product reads, after the images it came from had gone. This also made the privacy notice untrue, since that notice promises the video is deleted together with the still frames. Body-language scoring is off by default, so only sites that had switched it on were affected.

A course-data purge left the recording, the transcript and the video. Deleting a course's data removed seven tables including the scores, and never touched the recordings table. The score is the part anyone would check, so the purge appeared to have worked, while the video stayed in object storage and the transcript stayed on the row. This affected audio-only sites too, and predates the body-language work.

Deleting a course stranded every recording in the bucket. Three code paths delete recording rows and only one of them, the privacy erasure path, also deleted the stored media. Deleting an assignment, or deleting a whole course, dropped the rows and left the objects, and because the retention task finds expired media by walking those rows, nothing ever came back for them. Only a bucket lifecycle rule remained as a backstop. Deleting a course is the path administrators actually use.

FIXED: SCORING AND REPORTING

A criterion name is now matched the same way everywhere it is matched. Scoring decides three things from a criterion name: whether the model may score it, what maximum to divide by, and which course outcome the attempt records against. The first two ignored case and spacing and the third did not, so a model answering "evidence" for a rubric row called "Evidence" was scored, was shown to the learner, and silently recorded nothing against the outcome. Where two rubric rows now collide and disagree, nothing is recorded rather than one being chosen by array order, because an outcome attempt is permanent, visible only to staff, and cannot be appealed by a self-paced learner. The rubric editor refuses to save a rubric whose criterion names collide.

One rule decides whether a criterion counts, instead of four. The flag had four hand-written implementations giving three different answers for a small set of values, so a total could count a criterion that the table printing that total showed as not assessed.

FIXED: PRIVACY AND ACCESSIBILITY

Four tables that record which administrator configured the site are now declared to the privacy API: the model registry, the pricing feeds, the benchmark runs and the presentation assignments. None holds learner data and none is exported or erased, because removing them would delete the institution's model pricing, its price feeds and its benchmark history, and would reshape an assignment other learners are working against. Moodle core's own privacy test had been failing on three of them since 7.4.0.

The explanation of why a criterion was not assessed now reaches a screen reader. It sat in a title attribute on a badge that already had visible text, so most screen readers never announced it and the explanation was available only on hover.

TESTING

1,757 automated tests and 7,480 assertions, no failures. Security validator suite 36 of 36. Moodle core's own privacy suite passes. Tested against Moodle 4.5, 5.0 and 5.1 on PHP 8.1, 8.2 and 8.3, with both PostgreSQL and MariaDB.

Requires Moodle 4.5 or later.
