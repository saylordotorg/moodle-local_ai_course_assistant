# SOLA v7.0.3 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (21 August 2026)

Three retrieval capabilities that were blocked on adapter work, plus a design bug that live testing caught before it shipped.

### A query model that can be changed without re-embedding the corpus

The Voyage 4 family shares one embedding space, which means documents indexed with one member can be queried with another. Until now SOLA used a single `embed_model` for both sides, so changing the query model meant re-embedding all 75 million tokens of course content. A new **Query embedding model** setting decouples them.

This is dangerous if done carelessly, so it is guarded rather than merely offered. Vectors from different models are not comparable, and comparing them does not fail — it returns confident-looking cosine values that rank nothing correctly. That exact failure took ten minutes to diagnose on a dev site earlier this month. So every chunk now records the model that embedded it, and retrieval refuses to score a query against chunks it cannot be compared with, logging which model it skipped and why. A misconfiguration degrades to "no results for this course, with an explanation in the logs" instead of silently wrong answers.

Shared-space membership is declared by prefix in one place, so unreleased siblings are covered on the day they ship without a code change. `voyage-context-4` is deliberately excluded: it produces chunk vectors through a different pipeline and Voyage does not claim interchangeability with the plain 4 series.

**A caveat worth stating plainly.** This encodes a vendor claim, not a measured result. Benchmarking on our own corpus found asymmetric pairing was a wash for `voyage-4-lite` and 1.0 pp *worse* for `voyage-4` than querying with the model that indexed. Mixing is permitted but is not recommended on quality grounds — its real value is decoupling a query-model change from a full re-index.

### Quantized vector storage: a quarter, or a thirtieth, of the space

A new **Stored vector precision** setting selects full precision, reduced precision (one byte per dimension), or smallest (one bit per dimension). On the 86,206-chunk production index that is roughly 530 MB, 88 MB, or 11 MB.

Binary vectors are scored by Hamming distance over the packed bytes rather than expanded back into floats — 128 byte lookups per chunk instead of 1,024 float multiplications, so the smallest encoding is also the fastest to score.

Measured end to end against the live API on three documents and one query, reduced precision tracked full precision to within **0.0004** and both ranked the relevant document first. Smallest also ranked correctly.

### Contextualized chunk embeddings

`voyage-context-4` embeds a whole document in one pass so each chunk vector encodes its surroundings, rather than embedding each chunk in isolation. That is aimed squarely at our worst retrieval case: bare noun-phrase queries against chunks stripped of their document context.

It needs a different endpoint and a nested request shape, but the indexing pipeline already produced the grouping it wants — chunks carry `cmid` and `chunkindex`, so "the chunks of one document, in order" was already available. Requests are batched against the endpoint's documented limits with deliberate headroom.

Verified live: the same sentence embedded inside its document scored **0.795** cosine against the same sentence embedded alone. That gap is the proof the grouping reaches the model; had the nesting been wrong, each chunk would have been sent as its own document and the figure would have been exactly 1.0.

### The bug live testing caught

Binary similarity was first implemented on a [0, 1] scale, which is a natural-looking choice and wrong. Two unrelated vectors score 0.5 under it. Since `rag_min_similarity` defaults to 0.25 and is shared across all encodings, **every chunk would have cleared the floor** and the relevance filter would have silently stopped filtering.

Live scores made it obvious: 0.659 / 0.523 / 0.506 for one relevant and two irrelevant documents, against full precision's 0.499 / 0.062 / 0.019. The method now returns the raw sign-vector cosine, which puts unrelated vectors near zero exactly like cosine. Re-verified live: 0.318 passes the floor, 0.045 and 0.012 are filtered — matching full-precision behaviour. There is a regression test pinned to it.

This is only reachable by an administrator who switches to the smallest precision, so nothing shipped broken. It is recorded because the unit tests all passed against the wrong scale — the bug was invisible until real vectors went through it.

### Two fixes found along the way

- **The hash-skip optimization would have stopped working on quantized indexes.** It tested only the JSON vector column, which a quantized index leaves null, so every re-index would have re-embedded the entire course while appearing to work.
- **`send_message.php` caught `\Exception` where the rest of the retrieval path catches `\Throwable`.** Retrieval now calls `pack()`/`unpack()`, which raise `Error`, and an `Error` there has to degrade to "answer without citations" rather than fail the web-service call. `sse.php` already did this correctly.

### Two bugs found by reviewing the change itself

Neither was caught by a test, because both produce plausible behaviour rather than a failure.

**A separate query model was reported for providers that ignore it.** `get_query_model()` returned the configured value for every provider, but only the Voyage adapter sends it — OpenAI and Ollama embed with the document model unconditionally. Since retrieval uses that method for its comparability check, setting the option on an OpenAI site would have compared a model that embedded nothing against every stored chunk, judged them all incomparable, and returned no results at all, while holding a perfectly usable query vector. A capability is now claimed by the adapter that implements it, mirroring how the precision setting already worked.

**A byte length was taken with a text-length helper.** The storage figure used `sql_length()` on a binary column. That maps to `CHAR_LENGTH()` on MySQL and `LENGTH()` on PostgreSQL, and SQL Server needs `DATALENGTH()`. It gives the right answer on both databases the test matrix covers — a binary column carries the binary charset, so the two agree — but only by coincidence. It now counts rows per encoding and multiplies, which is portable and stays correct while an index holds a mixture of encodings part-way through a re-index.

### Accessibility

The RAG admin stat cards wrapped their numeric values in `<h3>`, injecting entries like "3" and "1,204" into the heading outline that screen-reader users navigate by. Those are now styled paragraphs — identical appearance, no phantom headings. A new card reports current vector storage, with a sentence estimating what other precisions would occupy.

### Testing

- **869 tests, 3,883 assertions, 0 failures.** 56 are new.
- Validator suite 36 of 36.
- Upgrade from v7.0.2 verified, with `check_database_schema.php` reporting the structure OK.
- All 46 locales lint clean; the translation-parity guard passes with no key staged as untranslated.
- Red-team cases are tested, not assumed: an out-of-range value clamps instead of wrapping its sign; a length-mismatched binary pair scores 0 rather than comparing the overlap; a corrupted encoding label reads as full precision rather than selecting a decode path the bytes do not match; every bit position is exercised individually so a shift error cannot hide in an aggregate.
- The source guard on vector writers was tightened rather than relaxed: it now also asserts that every packed write passes and records its encoding, and that the encoding comes from the provider rather than from config. The negative assertion was itself checked against a deliberately bad input to prove it is not vacuous.

### Internationalization

13 new strings across 46 locales — 598 translations. Placeholder and HTML-tag integrity verified programmatically in every locale.

Plugin version `2026082200`, release `7.0.3`.

## Part 3: Admin Walkthrough

Core drawer, quiz, voice, analytics, privacy, Soapbox and WSCUC-outcomes flows carry forward from v6.9.8. Two things are new.

### The settings page after the upgrade

Open Site administration → Plugins → Local plugins → AI Course Assistant → Settings on a site with default configuration. The feature toggles are all still there; their configuration is not, until you switch each feature on. Tick "Enable reranking" and its five fields appear inline.

If you had a feature configured before the upgrade, its settings are hidden but not lost — the values are still stored and reappear intact when you switch the feature back on. Nothing needs re-entering.

### Check your inactivity reminders

Worth two minutes on any site that runs learner email. Under Engagement, look at "Inactivity Reminders". If it is unchecked, this upgrade is the point at which that finally takes effect — those weekly emails were going out regardless before now. If you intended them to be off, nothing to do. If you find it unchecked and did want the emails, tick it.

### Rebranding

If you run SOLA under your own name, re-check the settings page after upgrading. Eight controls previously showed Saylor's branding regardless of what you had configured under Branding & UI; they now follow your `institution_name`, `institution_short_name`, `display_name` and `short_name`.
