# SOLA v7.5.7: Release Notes

## Part 1: Release Notes (28 September 2026)

**The assistant can now answer support questions outside a course.**

Until now SOLA only rendered inside a course. A learner who could not find the syllabus, could not submit an assignment, or could not work out how to get their certificate had no way to reach it. That is the population with the most urgent questions and the least ability to self-serve, and it is a large share of support volume.

Support mode is **off by default**. An administrator switches it on and names a real, visible course holding the getting started, onboarding and orientation material. The widget then appears on pages that are not a course -- the dashboard, a profile, the site home -- and answers from that course plus the site FAQ, with no course material and no pretence that the learner is in a course. When it cannot answer accurately it says so plainly and offers to pass the question to the support team, through the Zendesk escalation path that already existed.

### Two settings

- **Enable support mode outside courses** (`support_enabled`), default off.
- **Support course** (`support_courseid`), the ID of a visible course. The site home (course 1) is refused. An empty or unresolvable value turns the feature off rather than breaking anything, so a course that is later hidden or deleted degrades quietly.

Learners additionally need the new **Use the assistant outside a course** capability, which authenticated users hold by default and an administrator can revoke.

### Why it binds to a designated course, not to the site course

The obvious implementation is to render off-course and pass `SITEID` as the course id. That was measured against the code and rejected. `SITEID` is not a free slot; it already carries five distinct meanings in this plugin, and two of them would have produced wrong answers rather than merely untidy ones:

- **Conversations are keyed `UNIQUE (userid, courseid)`, and a SITEID conversation already exists.** Learning Radar writes user and assistant rows against it through `record_meta_query()`. `get_messages()` filters on role, not on interaction type, so a support turn at SITEID would have loaded the learner's Learning Radar prose as its chat history -- into the prompt and into the drawer.
- **The spend cap is per course.** Every user's support traffic across the entire site would have metered against the site course's single per-course cap.

Three more were merely wrong: `embedding_migration` enumerates courses with `courseid > SITEID`, so support chunks would have been invisible to a model migration, silently and forever; the system-prompt cache key collapses every non-course surface onto one entry per user for an hour; and about forty-five existing `require_capability(':use', context_course::instance($courseid))` sites -- including `get_config` and `get_history`, which the drawer calls before it can render anything -- would have had to learn a special case.

Binding to a real course avoids all of it by construction. The conversation gets its own row, spend meters against a course an administrator configures, the cache key is distinct, the migration can see the chunks, and every existing capability check keeps working against a context that genuinely exists.

### An exam-lock bypass, found before release

The first cut scoped the quiz lock to the course the widget was rendering against. `quiz_lock::active_attempt()` adds `AND cm.course = :courseid` under its default course scope, and the support course holds no quizzes -- so the lock matched nothing and never fired. A learner could open an exam in one tab, open the dashboard in another, and get an unlocked assistant during a graded attempt.

Every chat path now routes its course id through `support_mode::integrity_scope()`. In a course it returns the course id unchanged, so the v7.2.5 per-course scoping is exactly preserved; on the support surface it returns 0, which takes `quiz_lock`'s site-wide branch -- the conservative direction for an integrity control, and what that method's own docblock says to pass for a surface with no course of its own. Five call sites were changed: `sse.php`, `base_provider`, `send_message`, `generate_quiz` (twice) and the composer-greying check in `hook_callbacks`.

### Testing

`tests/support_mode_test.php` (21 tests) and `tests/support_mode_gate_test.php` (12 tests).

The load-bearing one is `test_a_live_attempt_elsewhere_locks_the_support_surface`, which asserts the bypass in both directions: that scoping to the support course finds nothing (the defect), and that the shipped code locks anyway. It is written against `quiz_lock` itself rather than against `integrity_scope()`'s return value, so it still fails if the two are ever unwired.

`test_every_chat_path_scopes_the_quiz_lock` reads the five files and fails on any `active_attempt` or `is_locked_for` call that passes a raw course id, so a future call site cannot silently reopen the bypass.

`test_both_gates_delegate_to_one_predicate` pins that the widget injector and the CSP header hook both ask `support_mode::renders_here()`. Those two have drifted before, and a page that rendered the widget without the CSP would lose the defence added after the injected-widget incident.

Four mutations proved through `scripts/prove_test.py`: removing the integrity-scope fallback, accepting SITEID, dropping the `visible = 1` filter, and making `require_use()` admit everything. All four caught.

The gate tests also caught a real defect during development: the exclusions for the plugin's own pages and the login flow were anchored with `strpos(..., '/local/...') === 0` against `moodle_url::get_path()`, which includes the subdirectory of a subdirectory install. They matched nothing under the test harness, whose wwwroot has one. Both now compare the wwwroot-relative path.

### What this release does not do

Not logged in. A learner who cannot get in at all still cannot reach the assistant. That case needs per-IP rate limiting (there is none today -- an unauthenticated streaming LLM endpoint is a token faucet), an anonymous identity for a `userid` column that is `NOT NULL`, and a privacy story for anonymous transcripts. It is tracked as Phase 2 of issue #261.

Course-only features stay course-only on the support surface: quiz generation, study plans, flashcards, voice and Soapbox all still require the per-course capability and refuse. That is deliberate -- they are about course material, and there is none here.

## Part 2: Key SOLA Features

- **Support mode outside courses (new in v7.5.7)** — optional, off by default. The assistant appears on the dashboard, profiles and the site home, answering enrolment, certificate and technical questions from an administrator-designated support course plus the site FAQ, and escalating to Zendesk when it cannot answer accurately.

Carried forward from v7.5.2. One new capability: the learner-facing **Your program
outcomes** panel (`outcomes_panel_enabled`, off by default), which reads program-level
attainment from the Outcome Map plugin and requires a version whose own-attainment
function accepts a course id. No other
feature changes. Soapbox remains deprecated, unchanged, and scheduled for code removal in
v8.0.0.

## Part 3: Admin Walkthrough

About twenty minutes. The order matters: the first two steps prove the release is safe
to have installed, and they are what every site sees on the day it is deployed.

### 1. Confirm the default is silence

Go to Site administration, Plugins, Local plugins, AI Course Assistant. Find "Enable
support mode outside courses". It is unticked, and "Support course" is empty.

Log in as a learner and open your dashboard. There is no assistant. Open a course you
are enrolled in: the assistant is there, exactly as before. That is the whole of the
change for a site that does not switch this on, and it is what every existing site will
see.

### 2. Tick it, and confirm nothing happens yet

Tick "Enable support mode outside courses" and save. Purge caches. Reload the dashboard.

Still nothing. That is correct, not a fault. Support mode needs somewhere to answer
from, so the feature stays off until "Support course" names a real, visible course.
Both halves are required, in both directions -- naming a course without ticking the box
does nothing either.

### 3. Point it at a course

Pick or create a course holding your getting-started, onboarding and orientation
material, and make sure it is visible. Put its numeric ID in "Support course" and save.
Purge caches.

Three things are worth trying deliberately here, because each fails quietly by design
rather than breaking a page:

- Enter `1` (the site home). It is refused, and support mode stays off. The site course
  already means several other things inside the plugin, and answering support
  conversations against it would collide with them.
- Enter the ID of a hidden course. Also refused. A hidden course is hidden from
  learners, and answering from it through the assistant would route around that.
- Enter an ID that does not exist. Also refused. A course that is later deleted turns
  the feature off rather than breaking every page on the site.

### 4. Open it as a learner who is enrolled in nothing

This is the case the feature exists for, so test it with an account that is not enrolled
in the support course -- ideally not enrolled in anything.

Reload the dashboard. The assistant is there. Open it and ask something the FAQ covers:
"how do I get my certificate?" You get the FAQ answer. Ask something your getting-started
course covers. You get that.

Now ask something that is plainly course material, like a question about a subject you
teach. It should decline to answer from course content and stay on support ground,
because in this mode it is told it is not in a course and must not redirect the learner
to course materials.

### 5. Check it is NOT everywhere

Still as that learner, confirm the assistant does not appear on:

- the login page
- any administration page
- the assistant's own pages under /local/ai_course_assistant/

And confirm that in an ordinary course you ARE enrolled in, the assistant still behaves
exactly as it did before: it answers from that course, not from the support corpus.

### 6. The exam lock, which is the one to actually test

Start a quiz attempt in any course and leave it open. In a second tab, open your
dashboard and open the assistant.

It must refuse, and say why. If it answers, stop and report it: that is an integrity
bypass, and it is the specific defect this release was written around. The support
surface deliberately uses the site-wide form of the exam lock rather than scoping to the
support course, because the support course holds no quizzes and scoping to it would mean
the lock never fires.

Finish or abandon the attempt, reload, and confirm the assistant answers again.

### 7. Escalation

With Zendesk configured, ask the assistant something it cannot answer and then ask to
talk to a person. It should say plainly that it cannot answer accurately and offer to
pass the question to the support team. Confirm the ticket arrives and carries the
conversation summary.

If Zendesk is not configured, the assistant is never told it can escalate, so it simply
says it cannot answer. That is intended: the alternative is promising a handover that
has nowhere to go.

### 8. Turning it off

Untick the setting, save, purge caches. The dashboard goes back to having no assistant,
and courses are unaffected. Nothing needs to be uninstalled or migrated, and existing
conversations in the support course remain where they are.
