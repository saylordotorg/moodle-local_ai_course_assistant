# SOLA v7.9.1: Release Notes and Walkthrough

## Part 1: Release Notes (17 October 2026)

## v7.9.1 (17 October 2026): deleting the default provider's row now warns that its old key still answers

The Providers and keys table copies the default provider's key into the old `apikey` setting, which every chat call reads. It only ever copies a key in. So if you deleted the default provider's row, for example because that key leaked or was revoked, the old key stayed in `apikey` and chat kept using it, and no screen showed or cleared it. 7.9.0 said nothing about that. The code review of the 7.9.0 pull request found it. This patch adds a warning. Nothing else changes: no new table, column, setting, scheduled task, capability or upgrade step.

- **The warning.** When the default provider has no key saved in Providers and keys, but an older default key is still saved and fits that provider, the next admin page shows: No key is saved for openai in "Providers and keys", but chat is still using an older default key. Deleting a row doesn't stop that key. Add a key for openai to replace it. The provider's name is in place of openai. The warning names the provider and never shows any part of a key.
- **When it appears.** On the next admin page after a save that changed the default provider, its model, **API Base URL** or the Providers and keys table, once per save. Deleting the default provider's row is the case it was written for. On **Auto** with a saved key it names the provider the model name points to. When no key is saved anywhere, the existing no-key warning applies instead.
- **Deleting a row doesn't stop the old key.** The key stays in the `apikey` copy and chat keeps using it. SOLA doesn't clear it for you, because on some upgrade paths that copy is the only copy of a key.
- **How to replace it.** Add a key for that provider in Providers and keys, either a new row with a key or **Change** on the existing row, and save. The copy takes the new key and the warning goes away. If a key leaked, replace it here first, then revoke the old one in the provider's console.
- **When it stays quiet.** It isn't raised when the provider needs no key (Ollama, Moodle AI), when **Auto** has no saved key (Moodle's AI subsystem answers), when the saved key looks like another vendor's (that case has its own warning, unchanged), when the row's base URL differs from **API Base URL** (that warning is unchanged too), or when `apikey` or the table is forced in `config.php`, where the copy is off by design. A custom provider with a base URL and a saved key now gets the warning when its row is gone, because chat is still sending that key.
- **Nothing else changed.** The other three default-provider warnings read and rank as they did.

**Known limits.**

- The warning is shown once, on the next admin page after the save. It isn't on Reports > Status, so if you dismiss it, nothing reminds you until you next save one of those four settings.
- Rolling back still means restoring the database from before the 7.9.0 upgrade. 7.8.x can't read the encrypted rows, and Moodle blocks a code-only downgrade.
- The new string is machine-translated into the 45 other languages, and a native speaker hasn't reviewed it, as with the 7.9.0 strings. All 45 translations are in this release.
- Saylor's production sites (Learn and Degrees) stay on 7.5.7, frozen until 2027. This release goes to the dev fleet and the Marketplace only.

### Testing

The full suite ran 2,887 tests with no failures and 7 skipped (7.9.0 ran 2,869). The new tests cover the warning in each case above, including deleting a row through the real table editor. CI passed on all nine PHP, Moodle and database combinations, along with the lint steps. After the deploy, dev.sylr.org and alpha.sylr.org both read build 2026101701. On both, the SOLA health check passed 8 of 8, the failover verifier's live probes through the table's keys passed (dev: Claude and OpenAI; alpha: OpenAI), a render of all 11 settings pages found no key value or ciphertext and no password input holding a value, and the new warning stayed quiet, as it should when the default provider has a keyed row.

Plugin version `2026101701`, release `7.9.1`. Change: #332.

## Part 2: Walkthrough (about 3 minutes (admin))

Nothing a learner sees changes in this patch.

1. Open Site administration > Plugins > Local plugins > AI Course Assistant > **AI provider and models**. Set **Default chat AI provider** to OpenAI and check that Providers and keys has an OpenAI row with a saved key. Save. No warning appears. (About 30 seconds.)
2. Press **Remove row** on the OpenAI row and save. The next page shows the new warning, with the settings-changed notice: no key is saved for openai, but chat is still using an older default key. Point out that it names the provider and shows no key text. (About 45 seconds.)
3. Say what's still true. Chat still answers with the old key, because deleting a row doesn't clear the `apikey` copy. SOLA leaves it alone on purpose: after some upgrades it's the only copy of a key. (About 30 seconds.)
4. Add the OpenAI row again with a new key and save. The next page shows no warning, because the copy took the new key. If the old key had leaked, this is the moment to revoke it in the provider's console. (About 45 seconds.)
5. Show that the quiet cases stay quiet. Set **Default chat AI provider** to Ollama or to Moodle AI (core_ai subsystem): no warning, because neither needs a key. (About 20 seconds.)
6. Upgrade from 7.9.0. The upgrade registers no new tables, columns, settings, scheduled tasks or capabilities, and it runs no new upgrade step. (About 10 seconds.)
