Hi Dean,

Could you run one read-only query against the Learn and Degrees databases and
send me the output? We're looking at what's driving database storage and I'd
rather work from the actual numbers than from what I can infer off our dev
fleet.

  SELECT table_name,
         ROUND((data_length + index_length) / 1024 / 1024 / 1024, 2) AS gb,
         ROUND(data_length  / 1024 / 1024 / 1024, 2) AS data_gb,
         ROUND(index_length / 1024 / 1024 / 1024, 2) AS index_gb,
         table_rows
    FROM information_schema.tables
   WHERE table_schema = DATABASE()
   ORDER BY (data_length + index_length) DESC
   LIMIT 25;

It only reads information_schema, so it takes no locks and touches no site data.
It runs in about 25 milliseconds on our dev fleet and is safe to run on a live
site at any time of day.

Separately, and only if it's easy: does either site have the Ad-hoc database
queries report (report_customsql) installed? If so we can run this sort of thing
ourselves next time rather than asking you.

Why I'm asking
----------------

We've been working through SOLA's own storage and found that its chunk table was
storing each embedding twice, once packed and once as JSON text. Clearing the
redundant copy freed about 59% of that table across our five dev sites, 392 MB in
total. We want to know whether the same is worth doing on Learn, and more
importantly whether SOLA is even a significant part of your storage picture or a
rounding error next to something else.

On dev the largest tables after our cleanup are the standard log and the Outcome
Map plugin's tables. Dev has almost no users though, so that ranking probably
doesn't hold on Learn. The tables that grow with users rather than with content
are the ones I expect to dominate at Learn's scale, which is exactly what the
query will show.

No urgency on this. Whenever it's convenient.
