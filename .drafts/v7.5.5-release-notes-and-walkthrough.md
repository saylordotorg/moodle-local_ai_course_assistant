# SOLA v7.5.5: Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (28 September 2026)

**Two defects a learner could hit, both found by driving the plugin as a learner rather than by reading it.**

- **Opening the assistant left keyboard focus behind.** `toggleDrawer` opened the drawer, gave it `role="dialog"`, and installed a Tab trap, but never moved focus into it. The trap only acts when the focused element is already the first or last control inside the drawer, so with focus on `<body>` it never engaged: a keyboard user pressing Tab walked the page behind the open dialog, and a screen reader user was given a dialog and then not placed in it. `closeDrawer` had always returned focus to the toggle; only the opening half was missing. Focus now moves to the message input, which is what someone opening an assistant wants and the one control in reach whose purpose is not "leave".
- **An oversized recording was refused with the wrong error, or billed.** The 25 MB audio cap in `transcribe.php` and `soapbox_transcribe.php` was unreachable on a default PHP configuration. PHP's `post_max_size` defaults to 8 MB, and when a request body exceeds it PHP discards the body entirely: `$_POST` and `$_FILES` both arrive empty, so the endpoint's own `require_sesskey()` is the line that fails, on a sesskey that went in the bin with the audio. Moodle answers that at HTTP 200 with an exception payload, so a learner who recorded a long clip was told their session was invalid and invited to log in again, and the server log recorded a CSRF failure that never happened. Separately, a file over `upload_max_filesize` (PHP default 2 MB) leaves `tmp_name` empty exactly as an absent file does, so it was reported as "No audio file provided" with HTTP 400. Both are now detected and answered with 413, the same status the 25 MB cap gives, so the three ways an upload can be too large give one answer.

Neither was visible in the existing tests. The focus defect is not expressible in PHPUnit, and the size defect sat in the one file PHPUnit cannot enter: `transcribe.php` declares `AJAX_SCRIPT` and gates on `is_uploaded_file()`, so the unit tests could only read its source and assert the guard was written and correctly ordered. It was, and it still never ran.

- **Seven learner-facing errors were wrong, five in language and two in kind.** `transcribe.php` answered a learner with `Audio file too large.`, `No audio file provided.`, `Unsupported audio format.`, `No voice provider configured for transcription.` and `Invalid transcription response.` as English literals, in a plugin that ships 46 locales. `soapbox_transcribe.php` had three of the same. They are now `voice:error_*` strings, translated into all 45 non-English locales, and both endpoints use them.

  The other two were not a language problem. `STT endpoint failed SSRF validation` names an internal host an administrator chose, and tells whoever triggered the request what the server can and cannot reach. `Transcription API error 401` says which upstream failure a caller provoked. Both now go to `debugging(..., DEBUG_DEVELOPER)` with the detail an administrator needs, including the rejected URL and the upstream host, and the learner gets the half they can act on: transcription is not set up, or it is not available right now. No response body from either endpoint carries a diagnostic any more, and a test asserts that every `['error' => ...]` payload in both files is a `get_string()` call.

### What went in to keep them caught

- `security::oversized_post_was_discarded()` and `security::upload_error_is_size()` lift both new guards out of the endpoints and into code a test can call. Six tests cover them, including the case that must NOT be answered with 413: a genuine POST with no body.
- The two Behat scenarios reverted at v7.5.4 are back and green. The panel sweep now enables the mastery dashboard for the generated course at run time, because the Progress control is wrapped in that condition and the config key contains the course id, so it cannot be written before the generator has assigned one. The oversized-clip scenario now captures the response body, which is how the `post_max_size` mechanism was identified rather than guessed at.
- Eleven mutations were planted and all eleven were caught. On the size guards: the discarded-body guard removed, the same guard moved after `require_sesskey()` where it is useless, `UPLOAD_ERR_NO_FILE` folded into the size class, and the CONTENT_LENGTH condition dropped so every empty POST would 413. On the new setting: the PHP ceiling ignored so a configured 50 MB is enforced on a server that passes 8, an unsaved setting read as 0 MB (which is every site on upgrade day, and 0 MB refuses every recording ever made), `-1` parsed as minus one byte rather than as "no limit", and an endpoint left reading the constant so the setting does nothing. On the error messages: the SSRF diagnostic put back in the response body, the upstream status code put back in the response body, and a single learner string reverted to an English literal.

Everything else in this release is v7.5.4 unchanged. See the v7.5.4 notes for the help panel fix, and the v7.5.3 notes for the program outcomes panel, the translated strings and the correctness work.

### The recording size limit is now a setting, and it tells you the truth

**Maximum recording size (MB)**, `max_audio_mb`, default 25, range 1 to 200. It sits in the voice section of the plugin settings.

The setting alone would have been a number you can type and be wrong about, so the description under it reports what PHP on your own server will actually accept:

> On this server PHP allows post_max_size = 8M and upload_max_filesize = 2M, so the size actually enforced right now is 2 MB.

The smaller of your setting and PHP's own limits always wins, and `security::max_audio_bytes()` applies that silently, because a larger configured number is not a preference that got overruled, it is a number that cannot happen. If PHP is the thing doing the capping the description says so in red and tells you which two directives to raise.

This is the part worth reading twice: PHP's defaults are `post_max_size` 8 MB and `upload_max_filesize` 2 MB, both below SOLA's 25 MB default. On a stock server the 25 MB cap has never been the cap. Ask your host what these are set to before telling learners they get 25 MB.

Nothing changes for an existing site on upgrade. `max_audio_mb` defaults to 25, which is what the hardcoded constant was.

## Part 2: Key SOLA Features

Carried forward from v7.5.2. One new capability: the learner-facing **Your program
outcomes** panel (`outcomes_panel_enabled`, off by default), which reads program-level
attainment from the Outcome Map plugin and requires a version whose own-attainment
function accepts a course id. No other
feature changes. Soapbox remains deprecated, unchanged, and scheduled for code removal in
v8.0.0.

## Part 3: Admin Walkthrough

The order matters here. Steps 1 and 2 are the ones every site can run, including one
without Outcome Map, and they are the ones that prove the release is safe to have on.
Steps 3 onward need an Outcome Map whose own-attainment function accepts a course id,
and a learner with real attainment.

### 1. Confirm the default is silence

Go to Site administration, Plugins, Local plugins, AI Course Assistant. Find "Show
learners their program outcomes". It is unticked.

Open a course as a learner and open the assistant. Go to the Progress tab. You see the
usual mastery panel and nothing else. That is the whole of the change for a site that
does not use Outcome Map, and it is what every Saylor site will see on the day this is
deployed.

### 2. Tick it, and confirm nothing happens yet

Tick the setting and save. Purge caches. Reload the learner view.

Still nothing. That is correct, not a fault. The panel needs an Outcome Map whose
own-attainment function accepts a course id, which
exposes a function that can report a learner their own attainment. Without it the only
route to that data needs a site-level capability no student has, so the panel refuses to
render for anyone rather than rendering for administrators only. Untick it again if you
are not ready.

Worth understanding rather than skipping: a panel that appears for staff and never for
the learners it describes is the worst outcome available, because the people checking
whether it works are the only people it works for.

### 3. With a sufficient Outcome Map: a course that uses outcomes

Pick a course that belongs to a program in Outcome Map and a learner with at least one
released result. Open the assistant as that learner, Progress tab.

Under the mastery panel there is now a "Your program outcomes" section, one block per
program, one row per outcome.

### 4. Read a row that has no number, which is most of them

Most rows will have no percentage. Each one says why in a sentence, and the sentences
differ: not enough evidence has been collected yet, a calculation is queued, the figure
is out of date, the result is calculated but not released, the outcome is not assessed in
this program.

Check that none of them shows 0%, an empty cell, or a bar drawn at zero width. On the
production degrees site, 525 of 546 result rows have no number, so this is the normal
view rather than an edge case. A learner reading a wall of zeroes would conclude they had
failed outcomes nobody has measured.

### 5. Confirm the panel is absent on a course that does not use outcomes

Same learner, a course that belongs to no program. The section is gone entirely, not
present and empty. The learner still has program results; they are just not relevant to
the course they are looking at.

### 6. Confirm it is the learner's own data and only theirs

Log in as a teacher on the same course and open the assistant. The teacher sees their own
progress panel, not the learner's. There is no path in this feature that shows one
person's attainment to another: the function it calls takes no user id at all, so there
is no request it can be made to answer about somebody else.

### 7. Turn it off and confirm it goes away

Untick the setting, save, purge caches, reload. The section is gone on the next page
load, with no deploy. That is the intended way out if it behaves badly, and it is the
reason the setting exists at all in a release that ships just before a long quiet period.
