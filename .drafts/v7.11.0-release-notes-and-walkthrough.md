# SOLA v7.11.0: Release Notes, Feature Summary, and Admin Walkthrough

## Part 1: Release Notes (19 October 2026)

## v7.11.0 (19 October 2026): find a key, replace it everywhere

**Why this release exists.** One API key can be stored in many places at once: a row in Providers and keys, a pasted Embedding or Rerank key, a Voice row, the old `apikey` copy of the default key, and the AI settings of individual courses. In one audit, the same OpenAI key was found in nine course configs across two sites. Replacing a key meant finding every copy by hand, and a missed copy meant a course that broke the day the old key was revoked. This release shows where each key is stored and replaces it everywhere with one command. It changes no data: no new setting, no schema change.

**See where a key is stored.**

- `admin/cli/rotate_key.php --list` prints every stored key as a fingerprint and its last four characters, with each place that holds it. It looks in the rows of Providers and keys, the five pasted-key settings (Embedding, Rerank, the embedding migration target, Realtime and self-hosted speech-to-text), the Voice providers rows, the legacy `apikey` setting, and the key saved on a course's own AI settings page. It never prints a key. The fingerprint is a keyed hash, so it's safe to show, and it's how you pick one key when two keys end in the same four characters.
- A new check under **Reports > Status**, "AI Course Assistant key places", lists each key that is stored in two or more places: the last four characters, the vendor, and the places, named by provider, setting name or course short name. The automatic `apikey` copy of the default provider's key doesn't count as a place, so a key needs two places of its own before it's listed. The check is always INFO. It's advice, not a fault. It lists at most 10 keys and 12 places for each.
- A key shorter than 12 characters has no last four. It's shown without one and picked by fingerprint.

**Replace a key everywhere.** Name the old key with `--old-last4=ab12` (or `--old-fingerprint=` from `--list`). Give the new key in an environment variable, `SOLA_NEW_KEY` or another name with `--new-key-env=NAME`, or on standard input with `--stdin`. The command prints what it would change and stops. Add `--apply` to make the change.

```bash
read -rs SOLA_NEW_KEY; export SOLA_NEW_KEY
php local/ai_course_assistant/admin/cli/rotate_key.php --list
php local/ai_course_assistant/admin/cli/rotate_key.php --old-last4=ab12            # dry run, changes nothing
php local/ai_course_assistant/admin/cli/rotate_key.php --old-last4=ab12 --apply    # replace it everywhere
```

Run it from the Moodle root as the web server's user. With `--apply` it replaces the key in every place that holds it, in one database transaction: the Providers and keys rows, the Voice providers rows, each pasted-key setting and the legacy `apikey` setting that held the key, and each course that held it. It then drops the cached settings and, when a Providers and keys row or the `apikey` setting held the key, re-syncs the `apikey` copy of the default provider's key, so chat uses the new key at once. It reads the stores back to check the new key is there, and prints how many places changed and the last four characters of the new key. One `key_rotated` row goes in the audit log, holding the vendor, the fingerprint, the old and new last four characters and the number of places of each kind. Exit codes: 0 done, 1 error or refused (also the rare case where the rotation was saved but couldn't be confirmed; the message says which, so read it before you revoke the old key), 2 no stored key matches or more than one does.

**Safety rules.**

- **A dry run first.** Nothing changes without `--apply`.
- **The new key never goes on the command line.** It would end up in your shell history and in the process list. `--new-key`, `--newkey`, `--key`, `--apikey` and `--old-key` are refused before anything is read, and so is any unknown option or argument. The message never repeats what you typed, in case it was a key, and it says to treat a real key typed there as exposed.
- **No key in any output.** Nothing the command prints, logs, audits or throws holds a key, its encrypted form or any part of it beyond the last four characters of a key of 12 or more characters.
- **An ambiguous old key is refused, never guessed.** If two different keys end in the same four characters, the command lists their fingerprints and stops. Matching on the last four is case-sensitive. A last four that matches nothing is refused too.
- **A key from another vendor is refused.** If the new key's prefix clearly names a different vendor than a place it would go into (`sk-ant-` is Claude, `sk-proj-` is OpenAI, `AIza` and `AQ.` are Gemini, `sk-or-` is OpenRouter, `xai-` is xAI), nothing is written. The message names the place and the vendor, never the key. A key without one of those prefixes isn't checked. Neither is a place with a base URL of its own or a provider of `auto`, `custom`, `ollama` or `coreai`.
- **A bad new key is refused.** It must be 8 to 512 characters of printable ASCII: no space, no tab, no line break, and no non-breaking or zero-width space that came along with a paste. It can't hold `|`, which the key table uses between columns, and it can't be the old key again.
- **A key forced in `config.php` blocks the whole rotation.** The command can't write `config.php`. Rather than leave a copy behind and say it worked, it refuses and names the place. Put the new key in `config.php` first, then run it again.
- **All or nothing.** Every write and the audit row run in one transaction. If any of them fails, or a store changed since the command looked, everything is rolled back, the cached settings are dropped and the command says nothing changed. If the change is saved but the command can't confirm it (reading back failed), it says so and tells you to run `--list` before you revoke the old key.
- **The key table is edited as text lines.** Every other row, comment, blank line, column, space and line ending stays byte for byte as it was, including a plain-text row from before keys were encrypted.

**Also fixed.** On a course's AI settings page, a course whose settings row has no key at all was shown as if it had one: the "saved" placeholder and the remove-key checkbox. Rows made by a course restore are inserted without a key, so restored courses showed it. A row with no key now shows neither.

**What the upgrade does to your site.** Nothing. There's no upgrade step, no schema change, no new setting and no new capability. **After you upgrade, purge caches,** as with any release that adds strings.

**What this does not do.**

- It doesn't revoke the old key at the vendor. Check that SOLA still answers, then do that yourself.
- It handles AI provider keys only. The Zendesk token, the Redash keys, the spend export key, webhook URLs, avatar vendor keys and Soapbox storage keys aren't listed or replaced.
- It doesn't see a copy of a key that an upgrade set aside. The 7.9.0 upgrade keeps the old key of a row it overwrote, concealed, in `provider_keys_displaced`, on sites where that happened. That setting isn't listed and isn't touched.
- It doesn't touch database backups, exports, or anywhere else you pasted the key outside SOLA.
- It can't replace a key in some places and not others. There's no option to skip one.
- The Reports > Status check doesn't mark a store that's forced in `config.php`. The dry run does: it prints `FORCED IN config.php` for it and stops without changing anything, because a forced value can't be rotated from here.
- It can't be used on Learn or Degrees yet (see Production).

**Not built: named key rows.** An earlier plan proposed giving every row of Providers and keys a stable name that roles, courses and the pasted-key boxes could select, instead of each holding its own copy of the key. That would let us remove the pasted-key boxes, give courses key profiles and build a Model roles table. It isn't in this release because today's key table can't carry it safely:

- A row is known only by its provider id, and the code always uses the first row for a provider that has a key, so a second row for the same provider can never be selected. Failover lines (`chat:openai`) name a provider, not a row.
- The row checker refuses some row shapes that a migration would need to write.
- Three things change the model settings directly, not through the settings page: the signed policy bundle, the automatic model-upgrade switcher and the benchmark command. A new control on the table wouldn't govern them.
- One control that holds several keys makes Moodle send every admin to the upgrade-settings page whenever its stored value is missing, and it drops the show/hide rules of the settings it replaces.
- A test requires at least 14 credential fields, so removing the pasted-key boxes means changing that floor on purpose. The lines of the course settings page that touch a key are listed word for word in another test, so changing them is deliberate too.
- A key profile for each course needs a new column on the per-course table, and backup, restore and a test that reads the source each list that table's columns by hand.

Named key rows are still possible, and any plan for them starts from this list. This release fixes the pain behind the proposal instead, which was rotating one key that lives in many places.

**Decisions behind this release.**

- The release was re-scoped from three items (a Model roles table, pasted keys moved into the key table, course key profiles) to this one, after reading the code. None of the three could be built safely on today's key table.
- Dry run by default, and no key on the command line, ever.
- A place forced in `config.php` blocks the whole rotation. It isn't skipped.
- The automatic `apikey` copy doesn't count toward "stored in two or more places".
- The new strings are English only (see Known limits).
- Marketplace upload isn't part of this release.

**Known limits.**

- The 17 new strings of the status check show in English in every language. They're listed in `KNOWN_UNTRANSLATED`, the same approach as 7.8.9, 7.9.1 and 7.10.0. A translation batch follows. The command's own messages are English text.
- The audit row names the site's main administrator account, because a command-line run has no signed-in user.

**Production.** Saylor's production sites (Learn and Degrees) stay on 7.5.7, frozen until 2027. 7.11.0 reaches them only when Catalyst upgrades them, so until then a key on Learn or Degrees is still replaced by hand. This release goes to the dev fleet (dev.sylr.org and alpha.sylr.org) and GitHub. The Marketplace upload isn't part of it.

### Testing

- 76 new tests across five files. Where a key could leak, the test plants a sentinel key and searches every output form for it: `json_encode`, `print_r`, `var_export`, anything printed, the audit row, and every 8-character piece of the key and of its encrypted form.
  - `key_inventory_test` (6 tests, 318 assertions): every kind of place is found, the same key gets one fingerprint wherever it sits, two keys with the same last four get different ones, a value this site can't decrypt is skipped quietly, and no output form carries a key.
  - `provider_keys_replace_test` (10 tests, 73 assertions): replacing a key in the key table changes only the matching lines. Every other line is checked byte for byte, including a plain-text row with a base URL, a comment line, a blank line and Windows line endings.
  - `key_rotation_test` (29 tests, 11,806 assertions): every kind of store is rotated; an ambiguous or missing key, a key of another vendor, a bad new key and a place forced in `config.php` each change nothing; a failure in the middle of the writes, or in the audit write, rolls everything back, and a failed read-back is reported as "could not be confirmed"; the `apikey` copy follows the new key; a stale cached setting isn't served after the commit; and a source scan holds the command to printing through `cli_writeln` and `cli_error` and to refusing any key on the command line before it reads anything.
  - `key_places_check_test` (26 tests, 448 assertions): the check is INFO in every state, the automatic copy doesn't count toward two places, the list is capped, and nothing carries a key.
  - `course_stored_key_display_test` (5 tests, 26 assertions): a course row with no key shows no saved key, rendered through the real template.
- The guards that matter most were each proven by planting the defect and watching a test fail, with `scripts/prove_test.py`: a `var_dump` of a key in the inventory, the key table rebuilt instead of edited line by line, the vendor check skipped, the transaction removed, the `apikey` re-sync removed, the cache drop after the commit removed, the audit encoding flags removed, the printable-ASCII rule loosened, and the mirror counted as a place.
- The command was run against the local test site with a disposable key: `--list`, a dry run, `--apply`, and each refusal (a key on the command line, an unknown argument, no match). No key was printed, and the setting was put back afterward.
- No chat, prompt, provider or retrieval code changed in this release. The other changes are the new classes, one method added to `provider_keys` and one to `voice_registry` that only the rotation calls, one line in `course_settings.php`, and the status check registered in `lib.php`.
- Release step, not filled in yet: the full suite on the release commit, the CI result, and the dev and alpha deploy check.

Plugin version `2026101802`, release `7.11.0`.

## Part 2: Key SOLA Features

What the plugin does as of v7.11.0, for an admin deciding what to switch on.

- **A tutor that knows the course.** Answers come from the course itself, with
  optional semantic retrieval over pages, books, PDF, DOCX, PPTX, H5P and SCORM
  content and video transcripts.
- **Practice built in.** Practice quizzes, flashcards, worked examples, study
  plans with reminders, and essay feedback against a rubric. Practice only,
  never a Moodle grade.
- **Steps back during assessment.** While a learner has a quiz attempt open, the
  assistant is unavailable to them everywhere, including outside the course.
- **Support outside courses** (optional). On the dashboard and site pages it
  answers enrolment, certificate and technical questions from a support course
  and the FAQ, with its own three starters, and can hand off to Zendesk.
- **Readable answers.** Headings, lists, tables, quotes and code render in the
  chat, and an answer that runs out of room says so rather than stopping
  silently.
- **46 languages**, with automatic reply-in-your-language, speech input and
  output, and an optional live voice mode. Works on phones, including with
  Moodle's menu drawer open.
- **Any provider, one table of keys.** Gemini, OpenAI, Claude (including Opus
  5.5 and Sonnet 5.5), DeepSeek, Mistral, xAI, MiniMax, OpenRouter, Together,
  Ollama, Moodle's own AI subsystem, or any OpenAI-compatible endpoint. Every
  provider's key, models and base URL live in one **Providers and keys** table,
  so you can add or change a key without touching the default provider.
  Embedding, Rerank and Voice can use a row's key instead of a pasted copy.
  Failover, a premium tier for hard turns (Claude Sonnet 5, benchmark-backed),
  and spend caps per course.
- **Keeps up with new models.** It knows what each model accepts from data
  rather than name checks, fixes a rejected request by itself, and (unless an
  admin turns it off) tests newer models nightly and switches to one that's
  the same price or cheaper and at least as good, rolling back if live answers
  get worse.
- **Costs you can see.** A model registry with prices and their sources, a daily
  price-drift check, token analytics, cost anomaly alerts and benchmarks.
- **Safe defaults.** Nothing contacts a third party until an admin configures
  it: remote configuration, the Python sandbox runtime and the CDN delivery all
  default to off. The assistant opens by itself only on course pages, and only
  if an admin turns auto-open on.
- **Keys encrypted at rest, never shown, and replaced in one step.** Provider
  keys, the Voice providers table, webhook URLs and every other secret are
  stored with Moodle's own encryption, so a database backup alone doesn't
  reveal them. No settings page ever shows a key: a saved one reads "Saved, ends
  in ab12", and the settings-changed notice and Moodle's configuration log hide
  secrets too. A command lists where each key is stored (by its last four
  characters only) and replaces one key everywhere in a single transaction, and
  a Reports > Status check flags a key kept in several places.
- **White-label.** Four settings rename the whole product, in every language.
- **Instructor views.** Analytics, a review queue for learner feedback, Learning
  Radar, transcripts with pseudonyms, and surveys with validated rating scales.
- **Python sandbox** (per course). Runs in the learner's browser, never on the
  server, and shows the full error when code fails.
- **Soapbox** remains deprecated, and no release removes it until PresenterAI can
  import existing recordings and scores; its replacement is the standalone
  PresenterAI activity.

## Part 3: Admin Walkthrough Script: replacing a key (about 10 minutes, conversational)

This is written to be read aloud while you click and type. It assumes a test site on 7.11.0 (the dev fleet is the place for it), an admin login, shell access to the server, and two keys from the same vendor: one that is already stored in at least two places, and a new one to replace it with. Don't use a production key to rehearse. For the rest of the menu, see the 7.10.0 walkthrough. For the key table in full, see the 7.9.0 walkthrough.

### 1. See where a key lives (about 2 minutes)

Open **Site administration, Reports, Status** and find **AI Course Assistant key places**. "This one's advice, not an alarm, so it's always blue." The summary reads "N API key(s) are stored in more than one place." Under it, each key is named by its ending and its places, for example: "The key ending in ab12 (openai key) is stored in 3 places: the Providers and keys row openai, the embed_apikey setting, course BUS101."

"There's no key on this page, only the last four characters. And the old `apikey` setting doesn't count as a place, because it's an automatic copy of the default provider's key. A key shows up here when it sits in two places you could edit yourself."

Now the shell, from the Moodle root:

```bash
sudo -u www-data php local/ai_course_assistant/admin/cli/rotate_key.php --list
```

It prints something like this:

```
1 key is stored.

0123456789ab  ends in ab12  openai  3 places: row 1, pasted 1, course 1
    row openai [openai]
    pasted embed_apikey [openai]
    course BUS101 (Business 101) [openai]
```

"One line for each key: a fingerprint, the last four characters, the vendor if the key's prefix says, and how many places hold it. Then one line for each place. The fingerprint is a keyed hash. It's safe to show, and it's how you pick a key when two share an ending."

### 2. Hand it the new key (about 1 minute)

"The new key never goes on the command line. It would end up in your shell history and in the process list for anyone on the server. So it goes in an environment variable." Type `read -rs SOLA_NEW_KEY`, paste the new key (nothing shows as you paste) and press Enter, then `export SOLA_NEW_KEY`.

"Sudo usually drops your variables. If it does here, pipe the key in instead":

```bash
printf '%s\n' "$SOLA_NEW_KEY" | sudo -u www-data php local/ai_course_assistant/admin/cli/rotate_key.php --old-last4=ab12 --stdin
```

"`printf` is part of the shell, so the key doesn't show up in the process list that way either." To see the refusal, type any made-up value after `--new-key=`. The command stops before it reads anything and says to treat a real key typed there as exposed. Don't try this with a real key.

### 3. Do a dry run (about 2 minutes)

```bash
printf '%s\n' "$SOLA_NEW_KEY" | sudo -u www-data php local/ai_course_assistant/admin/cli/rotate_key.php --old-last4=ab12 --stdin
```

It prints the key and its places again, then: "Dry run: nothing was changed. Run again with --apply to replace the key in 3 places." "Nothing has changed. This is where you check the list of places is the one you expected. The last four are case-sensitive, by the way."

Two refusals are worth seeing. Name a last four that two different keys share, and it lists both fingerprints and stops with exit code 2: "It won't guess." Then give it a new key whose prefix belongs to another vendor, say a Claude key (`sk-ant-`) for a key that's used with OpenAI. It writes nothing and says something like "row openai is used with openai, and the new key looks like a claude key." "It names the place and the vendor, never the key."

### 4. Apply it (about 2 minutes)

```bash
printf '%s\n' "$SOLA_NEW_KEY" | sudo -u www-data php local/ai_course_assistant/admin/cli/rotate_key.php --old-last4=ab12 --stdin --apply
unset SOLA_NEW_KEY
```

It prints the places once more, then: "Replaced the key in 3 places: row 1, pasted 1, course 1." and "The new key ends in" its last four characters. "That was one transaction. Either every place got the new key, or none did."

Open a course and ask the assistant a question. "If the old key was the default provider's, the `apikey` copy was updated too, so chat should answer straight away." If it does, revoke the old key at the vendor. "Do that last, and only then. The command doesn't do it for you."

### 5. Check the result (about 2 minutes)

Reload **Reports, Status**. The key now ends in the new last four characters, and the old ending is gone. Run `--list` again to see the same thing from the shell.

Then open the audit log from the quick links on **Essentials**. Find the `key_rotated` row. It shows the vendor, the fingerprint, the old and new last four characters, and the number of places of each kind. "Never a key. And it names the site's main administrator, because a command-line run has no signed-in user."

### 6. When it refuses or isn't sure (about 1 minute)

"Three messages to know." If a place is set in `config.php`, the command says so and changes nothing, because it can't write that file. Put the new key in `config.php` first, then run it again. If a store changed while the command ran, it says "A store changed while the key was being replaced. Nothing was changed," and you run it again. And if it says the change was saved but couldn't be confirmed, run `--list` and see where each key is now before you revoke the old one.
