WHAT IT FIXES

1. The objectives admin page stops walking every module in a course. Where a course had no mapped outcomes, the detector ran roughly four queries and one format_text() per Page and per Book chapter in that course with no cap, and wrote hundreds of identical "content must be processed with file_rewrite_pluginfile_urls()" debug warnings. It now reads approved outcome statements from local_outcomemap first, and where that yields three or more it returns before the walk ever starts, and the format_text() call sites pass the module's own context. local_outcomemap is installed on both sites. It holds no data on Learn, so nothing changes there; on Degrees 25 courses are mapped and those skip the walk, while the rest behave as before. This only ever ran when an administrator opened that page; no scheduled task calls it.

2. Embedding calls now retry. Embeddings were the only provider path with no retry: the first HTTP 429 threw, and the run is all-or-nothing, so an operator could not get out of it by retrying. It now uses the existing backend_retry_attempts and backend_retry_max_wait settings and honors Retry-After. FAQ indexing also makes one batched call instead of one request per question-and-answer pair.

3. Spend reporting counts what is actually billed. Token logging never read reasoning tokens and three endpoints persisted no usage at all, so the dashboard reported a floor rather than the bill: one month showed $3.96 of Gemini against an $11.13 invoice. The new column stores reasoning tokens and the previously unlogged call paths now report. Expect reported figures to rise after deploy with no change in actual spend.

4. Three ways a chat turn could fail are closed: a course restored from backup carrying a model the site cannot serve (every turn in that course returned HTTP 400), streaming provider errors that discarded the response body and surfaced as "[HTTP 400: ]" with nothing to diagnose, and prompt truncation that cut on byte boundaries and could split a multibyte character, which made json_encode() return false and send an empty body. None of these needs configuration.

5. Smaller user-visible changes, none needing action: teachers can place a Soapbox assignment on the course page (implemented as a core mod_url activity, so hiding, moving, availability, backup and restore are all core behavior), the Stop button no longer pushes a learner's just-sent question below the fold, the in-widget help panel follows the widget's language picker, and two admin pages previously reachable only by typing the URL are now linked from the settings tree.

There is no upgrade block for 2026091008; that version bump is code only. Only the first block touches a table with data in it. The models table holds 0 rows on both sites.

Production row counts in msgs, counted today: roughly 138,000 on Degrees (25 MB data, 37 MB index) and roughly 186,000 on Learn (52 MB data, 55 MB index). Both tables are ROW_FORMAT=Dynamic on Aurora MySQL 3.08.1 (VERSION() 8.0.39), read from information_schema.TABLES. On a Dynamic table at 8.0.39, adding a nullable column is an instant metadata change, so it does not scale with row count. We expect the plugin's own upgrade step to be sub-second on both sites.

As a ceiling rather than a prediction: our rehearsal box ran the tables as ROW_FORMAT=COMPRESSED, where InnoDB cannot use ALGORITHM=INSTANT and the ADD COLUMN becomes a full rebuild, which is why the rehearsal timings scaled with row count at all. At the worst rate measured there, 22.0 microseconds per row, the same step would take 3.03 s on Degrees and 4.09 s on Learn. That box is not representative of production, so treat those as an upper bound.

Either way this is seconds of database work, not minutes. What I do not have is your side of it: what is your estimate for the total window including your own process around the upgrade? That is the number we would schedule against.

WHAT THE REHEARSAL FOUND

The rehearsal ran 7.4.1 to 7.4.5 on a scratch Moodle with its own database. The db/ tree is byte-identical between v7.4.5 and v7.4.6, so the DDL set rehearsed is exactly what 7.4.6 runs; the 7.4.5 to 7.4.6 delta is code, one test and 46 language files.

The upgrade completed with no warnings and no errors. Afterwards the database was identical to a fresh install of the same build: 38 tables, 417 columns, 227 index rows, compared three ways (mysqldump DDL, information_schema.COLUMNS, information_schema.STATISTICS) with zero differences. Moodle's own admin/cli/check_database_schema.php reports "Database structure is ok." on both.

The db/upgrade.php change from v7.4.1 to v7.4.6 is one hunk, 152 lines added, nothing removed. No block a site has already run was edited, so nothing can re-run differently. Each of the four blocks ends with upgrade_plugin_savepoint() at 2026091002, 2026091004, 2026091005 and 2026091007, so a run that dies partway resumes from the last savepoint rather than redoing completed work.

The DDL is additive: one new table, three new nullable columns, one table comment. Nothing is dropped or rewritten and no existing row is touched, so please follow whatever your normal backup policy is for a plugin upgrade. Nothing here requires an extra snapshot on our account.

Maintenance mode is not needed from our side. Use whatever your process normally does. A learner mid-chat while the code is being swapped would see that one turn fail; the next message after the upgrade works normally.

One new scheduled task: collect_meta_ai_batches, on */30. The plugin goes from 22 scheduled tasks to 23 and nothing else in db/tasks.php changed. It polls for in-flight batch jobs and returns immediately when there are none, and the setting that creates those jobs is off by default, so on both sites it will do nothing until someone turns it on.

No new outbound destination, and nothing in this release starts traffic or sends mail on its own. The one network-behavior change is item 2 above: a rate-limited embedding run now makes more requests over a longer wall time instead of failing on the first 429, bounded by the existing retry settings. FAQ indexing goes the other way, from one request per pair to one request in total.
