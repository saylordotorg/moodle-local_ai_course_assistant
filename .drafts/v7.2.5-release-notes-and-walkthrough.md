# SOLA v7.2.5 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (29 August 2026)

### One forgotten quiz attempt disabled the assistant everywhere

A verification pass over 7.2.4 — which never got a tag, so this release carries
both — closed three of its six fixes, found two half-landed, and reported a P1:
SOLA refusing to answer in a course that contains no quizzes at all.

- **The quiz lock now stops at the course holding the quiz.** The report
  diagnosed this as the lock matching attempts that were no longer open. It was
  not: the query has always required `state = 'inprogress'`, and the two
  finished BUS 101 attempts were irrelevant. There was a genuinely open attempt,
  on a quiz called ZZ Quiz in an unrelated sandbox course, and the lock was
  site-wide.

  The real problem is larger than the report. About 88,900 attempts sit in
  `inprogress` on learn.saylor.org, 95% of them more than a month old, because
  nothing ever transitions an abandoned attempt out of that state. Site-wide
  scope means every one of those learners loses the assistant in every course
  they take, indefinitely, with nothing on screen to explain why. The integrity
  case for site-wide is thin — a learner set on cheating has a second browser,
  and the assistant's course material and retrieval are course-scoped anyway —
  so the default is now the course holding the attempt. The new
  `quiz_lock_scope` setting restores the old behavior for a site that wants it.

- **The drawer and the server now agree.** The widget never knew the attempt
  lock existed. Its `quizlocked` flag is the per-quiz assistance level, a
  different mechanism that only applies on a quiz page — so everywhere else the
  drawer rendered a normal, enabled textarea while the server was going to
  refuse, and a learner typed a whole question before finding out. Both sides now
  read the same check for the same course, and the refusal uses the server's own
  wording, which names the remedy.

- **Blocked quiz generation says why.** It returned "Could not generate a quiz.
  Please try again", inviting a retry that could never succeed. The lock case now
  returns the integrity message; genuine failures keep the retryable one.

- **A failed turn can no longer replay an exception class.** 7.2.4 fixed the
  writer and not the reader, so rows stored before it still rendered as
  `[no response: core\exception\moodle_exception]`. The renderer now substitutes
  a learner-facing notice for any stored internal identifier. That covers
  historical rows with no migration, and it covers the paths that bypass the new
  persistence entirely: provider timeouts, 5xx, failover exhaustion. The same
  scrub runs on the history fed back to the model — prior assistant output is an
  example it can imitate, and an exception class is the last thing it should
  learn to emit.

- **TOTAL STUDENTS reads correctly site-wide.** `get_enrollment_counts()`
  returned two different shapes: a `total_enrolled` key for a single course, and
  a bare list of per-course rows for all courses. The payload is `PARAM_RAW`
  JSON, so nothing validated it — the dashboard read `.total_enrolled` off a
  list, got `undefined`, and painted 0 next to 104 sessions. Site-wide now counts
  distinct learners, so someone enrolled in six courses counts once.

- **TOTAL STUDENTS also changed slightly per course**, and this is deliberate
  rather than a second regression: the count moved from `COUNT(ue.id)` to
  `COUNT(DISTINCT ue.userid)`, so a learner holding both a manual and a self
  enrolment in the same course is now counted once instead of twice. Any course
  with overlapping enrolment methods will read a little lower. Note also that
  this tile counts every enrolled user, teachers and admins included — unchanged
  behavior, now visible site-wide for the first time.

- **The privacy notice no longer contradicts the audit log.** It claimed SOLA
  "does not collect your full name" while an admin view showed one. It now says
  SOLA keeps no record of its own, and that a name appearing alongside SOLA data
  is read from the existing Moodle account.

### Upgrade notes

No schema change and no upgrade step. `quiz_lock_scope` defaults to **This
course only**; a site that wants the 7.2.4 behavior sets it to **Every course**.

If learners have reported the assistant being unavailable for no visible reason,
that is the bug this release fixes and it needs no action beyond upgrading.

### Testing

- 1,072 tests, 5,029 assertions, no failures (1 skipped).
- 36/36 validators. PHP lint clean across the plugin.
- i18n 46/46 complete; four new strings translated into all 45 non-English
  locales.
- Verified against the live dev database that produced the reports: the two
  courses that were wrongly locked are now free, only the course holding the open
  attempt locks, all five stored placeholder rows render safely, and the
  all-courses student count is non-zero and above the largest single course.

Plugin version `2026082901`, release `7.2.5`.

## Part 3: Admin Walkthrough

### 1. Finish a quiz and immediately ask a question

Start an attempt on a quiz in a course, confirm the drawer is disabled and shows
the integrity notice, submit the attempt, then send a message in the same course.

**Expected:** it answers immediately. The lock lifts on submission, not when a
freshness window expires. Before this release it would keep refusing — and would
also refuse in every other course you opened.

### 2. Confirm the lock does not follow you between courses

With an attempt open in course A, open the assistant in course B.

**Expected:** course B works normally. Only course A is locked. If you want the
old site-wide behavior, Site administration → AI Course Assistant → *How far the
lock reaches* → **Every course**.

Worth knowing why the default changed: an abandoned attempt stays `inprogress`
forever, so under site-wide scope one forgotten quiz anywhere in a learner's
history disables the assistant in all their courses permanently.

### 3. Check that the input is disabled exactly when the server will refuse

While an attempt is open, open the drawer in that course.

**Expected:** the textarea and all six starter chips are disabled, and the notice
names the remedy — submit or close the attempt. There should be no state where
the box looks usable and the send is then refused.

### 4. Reload a conversation that had a failed turn

Open a course conversation with history.

**Expected:** zero occurrences of `core\`, `exception`, or `moodle_` anywhere in
the transcript. Old rows stored before 7.2.4 render the same learner-facing
notice as new ones.

### 5. Analytics with All courses selected

Site administration → Analytics, picker on **All courses**.

**Expected:** TOTAL STUDENTS carries a real number, at least as large as any
single course and at least as large as ACTIVE AI USERS. Note these two measure
different things: TOTAL STUDENTS is active enrolments, ACTIVE AI USERS is people
who actually used SOLA, so the gap between them is your adoption rate.

### 6. Read the privacy notice next to the audit log

Open the learner privacy notice, then the admin audit log.

**Expected:** the notice says SOLA keeps no record of its own of your name, and
that a name shown alongside SOLA data comes from your existing Moodle account.
That should read as consistent with the audit log showing full names.
