# SOLA v7.1.1 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (26 August 2026)

### Four things we could not previously measure, and one that never worked

Every item here came out of the single-turn study. None changes what the assistant
says; they change what we can find out about it, which is what the study kept
running into.

#### A turn that fails is no longer indistinguishable from a learner leaving

9.5% of conversations contain a question with no stored answer. Until now that
could not be diagnosed, because the two explanations produced identical evidence:
`sse.php` writes the learner's message before calling the model and the reply only
after the stream finishes, the plugin never called `ignore_user_abort()`, and the
error path wrote nothing at all. A provider failure and a closed tab both left a
question and silence.

Three changes end that:

- `ignore_user_abort(true)`, so closing the tab no longer kills the request before
  the reply is recorded.
- A new `stream_outcome` column on the message row: `complete`, `client_aborted`,
  or `provider_error`.
- The error paths now persist a reply row carrying whatever had streamed, the
  exception class, and `provider_error`. Both catch blocks, not just one.

Rows written before this release stay `null` — honestly unknown, rather than
back-filled with a guess.

#### Retrieval is measured instead of inferred

New `chunk_count` and `top_score` columns record what retrieval actually returned.
The study had to infer this from `prompt_tokens`, a proxy that turned out to be
invalid because providers report that field differently — several replies logged
under 50 prompt tokens while returning the most thoroughly grounded answers in the
sample. `0` and `null` mean different things here and are stored differently:
zero is retrieval that ran and found nothing, null is retrieval that never ran.

#### The Quiz Me press is countable

The chip is type `quiz`: it opens a panel rather than sending a message, so a
learner who opened it and backed out left no trace anywhere. v7.1.0 made quiz
*generation* visible; this makes the *press* visible, so the gap between them —
the abandonment — is finally measurable. New external function
`record_quiz_open`, rate-limited at 60/minute, writing a `role='system'`,
`interaction_type='quiz_open'` row that carries no model and therefore no spend.

#### Language auto-detection was dead code

`sse.php` treats an empty `lang` as "detect the language from the learner's
writing". `ui.js` sent `lang || 'en'`, so it was never empty and detection never
ran once. A learner writing Spanish got English back — three of fifty sampled
transcripts. Now sends empty when the learner has expressed no preference; an
explicit choice still wins.

**Worth a decision for ESL courses.** All three sampled cases were ESL learners,
where answering in English is arguably the right pedagogy — the assistant said as
much. If that is your intent for ESL, set the course language explicitly rather
than relying on what was previously an accident.

### Upgrade notes

- **One upgrade step, three additive columns on the message table.** No drops, no
  renames, no data migration.
- **Three AMD bundles rebuilt** (`chat`, `ui`, `repository`), so purge caches.
- **Expect `quiz_open` rows to appear.** They carry no tokens and no model, so
  they do not affect spend or any cost figure.
- The three new columns are technical metadata, not personal data, so they are not
  declared in the privacy provider — consistent with `cached_tokens`,
  `rag_latency_ms` and `cmid`, which are also undeclared.

### Testing

Full suite 951 tests / 4,038 assertions / 0 failures. Validators 36/0. Lint clean.
The upgrade step was run against a real database and the three columns verified
present afterwards. All three rebuilt bundles were checked for the change **in the
built file**, not just the source.

Plugin version `2026082600`, release `7.1.1`.

## Part 3: Admin Walkthrough

Carries forward from v7.1.0. Two things are worth ten minutes.

### Ask the question the study could not answer

After a week or so of data:

```sql
SELECT stream_outcome, COUNT(*) FROM {msgs}
 WHERE role='assistant' AND stream_outcome IS NOT NULL
 GROUP BY stream_outcome;
```

`provider_error` is a bug to chase. `client_aborted` is a learner leaving
mid-answer, which is a product question, not an outage. Before this release both
looked the same, and both looked like nothing at all.

### Check the language behavior in one ESL course

Open the assistant in an ESL course and write a sentence in Spanish. You should
now get Spanish back. If you would rather ESL learners were answered in English,
set that course's language explicitly — do not rely on the old behavior, which was
a bug rather than a policy.
