# SOLA v7.9.0: Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (2026-10-16)

## v7.9.0 (2026-10-16): one table for provider keys, and no secret ever shown in settings

**Why this release exists.** Rotating an OpenAI key on 15 and 16 October looked like it required switching the default chat provider first, because the one API Key field belonged to whichever provider was the default, and saving would have rerouted every learner's chat. A review of the settings pages for that rotation also found real keys in the page source: the comparison providers table put each row's key in a password box (hidden on screen, readable in the page source) and stored the keys as plain text. This release fixes both.

**One table for every provider key.** Under **AI provider and models**, a new **Providers and keys** table has one row per provider: provider, API key, models, temperature and base URL. A saved key shows as "Saved, ends in ab12" with a **Change** button, so you can match it to the key in the provider's console. Leave the key blank when you save and the stored one stays. Rows for Ollama and Moodle AI can be saved without a key, which the old table couldn't do. The old **API Key** field is gone. **Default chat AI provider** now only chooses which row chat uses, and changing it never changes a key. Chat uses the key of the default provider's row only when that row's base URL is the same as **API Base URL** (both are compared with spaces trimmed, and an empty row URL matches an empty **API Base URL**). Behind the scenes the old `apikey` setting is an automatic copy of that row's key. It's copied again whenever the table, the default provider, the model or the base URL changes on the settings page (Moodle runs the copy only when a value actually changes). It's also kept in step after a signed policy bundle that changes the provider or model is applied, after the automatic model switcher changes the model, and after its rollback, so everything that read it keeps working.

**No secret in any settings page.** No SOLA settings page contains a key, token, webhook URL or the encrypted form of one. That holds on first load, on reload, after a save and after a failed save (a key you typed comes back as an empty box, with a message to type it again). A new test seeds a marker into every secret setting and every table row, renders every settings page through Moodle's own save path, and fails if a marker, a piece of one or any encrypted text shows up. The **Voice providers** table uses the same rows editor, and every single-key field shows "Saved key ends in ab12." under its description. A saved URL shows only "A URL is saved.", because the end of a webhook URL is part of its secret.

**Everything is encrypted.** The table's keys, which were plain text before, are now encrypted like the other secrets. So are the Slack and Teams anomaly-digest webhook URLs, which were plain text boxes. The webhook fields still check that the value is an http(s) address with a host and no user name or password.

**Embedding, Rerank and Voice can use a row's key.** Three new selects, **Embedding key source**, **Rerank key source** and **Voice and TTS key source**, let each one use the key from a provider row instead of a pasted copy. Voice offers OpenAI rows only, and uses the first OpenAI row that has a key and no base URL of its own (a gateway row listed before it is skipped). Embedding and Rerank skip a row key that's clearly another vendor's, unless a base URL is set for that feature, and use the pasted key instead. They also skip a chosen row that has its own base URL unless that URL is exactly the one the feature sends to, so an Azure or gateway key is never sent to the vendor's default endpoint. A trailing slash, or a URL that spells out the vendor's default endpoint, counts as a mismatch, and the pasted key is used. `voyage` is a new row type for Embedding and Rerank only, and the LLM pickers, the benchmark and the failover chain skip it: a `chat:voyage` failover line is reported as having no usable row. Nothing switches on by itself: an OpenAI row added for failover doesn't turn on the speak button, but choosing it as the Voice key source does, along with the Conversation Practice chip and the speech-to-text fallback, even with Voice Mode off. The RAG fixture benchmark command refuses to run while Embedding or Rerank points at a row, because the row would override the key each benchmark arm sets.

**Better warnings.** If **Model Name** is a display name such as "GPT-4o-mini" on a hosted provider, the next admin page after a save says so, as 7.8.8 already did for backup rows. The same page warns when the default provider has no key anywhere, or when the saved key looks like another vendor's. It also warns when the default provider's keyed row has a base URL of its own that differs from **API Base URL** and no keyed row matches: chat still uses the previous default key until the two match or you clear the row's base URL. That warning stays quiet on a site where `apikey` or the table is forced in `config.php`. A base URL in the table can't carry a user name, a password, a credential-like query parameter (key, token, secret, signature, auth, code and similar) or a `#` part, and a value saved earlier shows masked as `***`.

**Hidden in notices and logs.** The "settings changed" notice shows "changed (value hidden)" for a secret and "A saved key changed. Keys are never shown here." for a table row's key. When you save a SOLA secret on a settings page, Moodle's configuration log now records `********`, and for the two tables it records `********` in the key column (Moodle's own encrypted-password field used to write the whole encrypted value there). Rows written before 7.9.0 are still in the log. `php local/ai_course_assistant/admin/cli/audit_config_log_secrets.php` now also finds old rows for every secret this plugin lists (the two webhook URLs among them) and for both provider tables, and with `--redact` or `--ids=` overwrites them (only the key column, for the tables). The audit tool doesn't read `#` comment lines in a table, and it doesn't find or redact credentials in a row's base URL.

**What the upgrade does to your site.**

- It encrypts every stored secret still in plain text: the table's keys, the Voice providers keys and the two webhook URLs.
- The default provider gets a row carrying its key and base URL, only if it has no keyed row for the same base URL. It adds nothing, and says nothing, when the saved key's prefix clearly belongs to another vendor (for example `auto` with a Gemini key and no model name resolves to openai, so no openai row is filed). A gateway base URL turns that check off, because a gateway takes any key.
- If it already had a row with a different key than the one chat was using, the row takes the default's key. One notice names the provider and the last four characters of both keys. It shows on the first admin page you open in a browser after the upgrade, even when the upgrade ran from the command line. The key it replaced is kept, still encrypted, in the `provider_keys_displaced` setting for one release (a later release deletes it), and an audit row records the change.
- A key forced in `config.php` is never copied into the database. A table forced in `config.php` is never written, and it shows read-only.
- `auto` with no saved key (a site that uses Moodle's AI subsystem) gets no row and never starts using a direct provider.
- A site that configures nothing new behaves the same: the same key for the same call, the same failover chain, the same LLM picker. Four differences are visible. Voyage rows no longer appear in the LLM pickers or the benchmark. On `auto` sites the new default row adds a picker entry with no models, and a `chat:<primary provider>` failover line now resolves. Where a key conflict was resolved, comparison and failover use the default's key for that provider. And on `auto` sites, calls that name a provider by id (the mastery classifier's default `openai`, and quiz, essay and premium calls that name the resolved provider) used to refuse for lack of a row and now run on the new row.

**What it can't do.** 7.9.0 can't hold two different keys for the same provider and base URL as a primary and a failover backup. The default provider uses the key of its row for the matching base URL, and the first row with a key serves failover. You can list a provider twice (the golden tutor bake-off script reads two rows for one provider), and saving shows a warning that the first row with a key is the one used.

**Rolling back.** 7.8.x doesn't understand encrypted rows. The `apikey` copy still works, so the default provider's key does, but the row keys don't, because 7.8.x would send the encrypted text as the key. Moodle blocks a code-only downgrade, so a rollback means restoring the database from before the upgrade.

**After you upgrade.** Purge caches: a benchmark payload cached by an earlier release can still hold plain row keys until then. Then run the audit command above and read what it finds.

**Known limits.**

- Plain base URL text fields (`apibaseurl`, and the embedding and rerank base URLs) aren't masked. Only the table's base URL column refuses and masks credentials.
- Learning Radar schedule webhooks are still plain database columns. The page that reads them is admin-only.
- The admin presets export carries the encrypted value of every secret and of both provider tables, and applying a preset writes its raw values to the configuration log.
- A row keeps its key when you change the row's base URL host. Retype the key after moving a row to another host. A later release is meant to require it.
- A row with its own credential and an empty base URL still sends its key to a course's own gateway URL when that course sets one. That's how it worked before 7.9.0, and it hasn't changed.
- A table forced in `config.php` can leave a shadowed plain copy in the database if one existed before, because the upgrade doesn't touch a forced table.
- On `auto` sites, a course's own key isn't protected from the new default row for calls that name a provider by id (the fourth visible difference above).
- The Voice key-source select is hidden while Voice Mode is off, the same as the pasted key.
- On the all-settings hub page, a row and the key-source choice that names it can't both be applied in the same save, because the choices are built before the save. Use the individual pages.
- A typed key that only starts with an encryption prefix (`sodium:` or `openssl-aes-256-ctr:`) is stored as typed.

**Translations.** The 74 new or reworded admin strings are translated into all 45 other languages by machine, then checked by translating each one back to English without the original in view. That check found eight strings with the wrong meaning (in Bambara, Hausa, Yoruba and Zulu), and they were retranslated. The rest still need a native-speaker review, most of all in Wolof, Yoruba, Zulu, Tagalog, Bambara, Oromo, Somali, Hausa, Igbo and Amharic. The Tamil wording for "lowercase" needs a look too, and the existing Wolof and Bambara files use some terms inconsistently.

**Production.** Saylor's production sites (Learn and Degrees) stay on 7.5.7, frozen until 2027. This release goes to the dev fleet and the Marketplace only.

## Part 2: Key SOLA Features

What the plugin does as of v7.9.0, for an admin deciding what to switch on.

- **A tutor that knows the course.** Answers come from the course itself, with
  optional semantic retrieval over pages, books, PDF, DOCX, PPTX, H5P and SCORM
  content and video transcripts.
- **Practice built in.** Practice quizzes, flashcards, worked examples, study
  plans with reminders, and essay feedback against a rubric. Practice only,
  never a Moodle grade.
- **Steps back during assessment.** While a learner has a quiz attempt open, the
  assistant is unavailable to them everywhere, including outside the course.
- **Support outside courses** (optional). On the dashboard and site pages it
  answers enrolment, certificate and technical questions from a support course
  and the FAQ, with its own three starters, and can hand off to Zendesk.
- **Readable answers.** Headings, lists, tables, quotes and code render in the
  chat, and an answer that runs out of room says so rather than stopping
  silently.
- **46 languages**, with automatic reply-in-your-language, speech input and
  output, and an optional live voice mode. Works on phones, including with
  Moodle's menu drawer open.
- **Any provider, one table of keys.** Gemini, OpenAI, Claude (including Opus
  5.5 and Sonnet 5.5), DeepSeek, Mistral, xAI, MiniMax, OpenRouter, Together,
  Ollama, Moodle's own AI subsystem, or any OpenAI-compatible endpoint. Every
  provider's key, models and base URL live in one **Providers and keys** table,
  so you can add or change a key without touching the default provider.
  Embedding, Rerank and Voice can use a row's key instead of a pasted copy.
  Failover, a premium tier for hard turns (Claude Sonnet 5, benchmark-backed),
  and spend caps per course.
- **Keeps up with new models.** It knows what each model accepts from data
  rather than name checks, fixes a rejected request by itself, and (unless an
  admin turns it off) tests newer models nightly and switches to one that's
  the same price or cheaper and at least as good, rolling back if live answers
  get worse.
- **Costs you can see.** A model registry with prices and their sources, a daily
  price-drift check, token analytics, cost anomaly alerts and benchmarks.
- **Safe defaults.** Nothing contacts a third party until an admin configures
  it: remote configuration, the Python sandbox runtime and the CDN delivery all
  default to off. The assistant opens by itself only on course pages, and only
  if an admin turns auto-open on.
- **Keys encrypted at rest, and never shown.** Provider keys, the Voice
  providers table, webhook URLs and every other secret are stored with Moodle's
  own encryption, so a database backup alone doesn't reveal them. No settings
  page ever shows a key: a saved one reads "Saved, ends in ab12", and the
  settings-changed notice and Moodle's configuration log hide secrets too.
- **White-label.** Four settings rename the whole product, in every language.
- **Instructor views.** Analytics, a review queue for learner feedback, Learning
  Radar, transcripts with pseudonyms, and surveys with validated rating scales.
- **Python sandbox** (per course). Runs in the learner's browser, never on the
  server, and shows the full error when code fails.
- **Soapbox** remains deprecated and will be removed in v8.0.0; its replacement is
  the standalone PresenterAI activity.

## Part 3: 20-minute Admin Walkthrough Script (conversational)

This is written to be read aloud while you click. It assumes a test site on
7.9.0 (the dev fleet is the place for it), an admin login, and one provider key
you can paste. Step 5 changes the default provider for a minute, so don't do it
on a site where learners are chatting.

### 1. Clear the caches and look for one notice (about 2 minutes)

"First thing after any upgrade: purge caches, because an old cached benchmark
page can still hold row keys." Do that under **Site administration, Development,
Purge caches**. Then open any admin page. If the upgrade found two different keys
for one provider, a yellow notice names the provider and the last four characters
of both keys. It says the row now uses the default key, the one chat was already
using. Write the two endings down; if the row's old key was the one you meant,
you'll paste it again in step 4. Most sites won't see this notice.

### 2. Open "Providers and keys" (about 2 minutes)

"Now the page this release is about." Go to **Site administration, Plugins,
Local plugins, AI Course Assistant, AI provider and models**. Under the
**AI Provider & Conversation** heading there's a **Providers and keys** heading
with a table, and below it a **Default provider** heading with the **Default chat
AI provider** dropdown. There's no API Key field any more.

Look at the table. There's a row for your default provider (the upgrade made it
if it wasn't there and the saved key fit the provider), carrying its key and base URL. The columns are provider,
API key, models, temperature, base URL. The key cell reads "Saved, ends in" and
four characters, with a **Change** button. "Match that ending against the key in
your provider's console, and you know which key this is without ever seeing it."

### 3. Add a key without touching the default (about 3 minutes)

"Say you want a Claude key on file, for failover or the LLM picker, but you don't
want to disturb chat." Press **+ Add provider**. Pick **Claude (Anthropic)**, paste
the key into the empty box, and type a model name from the provider's list in
**Models**. Leave **Default chat AI provider** alone and press **Save changes**
at the bottom.

When the page comes back, the new row reads "Saved, ends in" and the last four
characters of what you pasted. The default dropdown still says what it said
before. The notice at the top lists the table as changed, and any key in it
shows as `********`. "That's the whole point: a key went in, and chat didn't
move."

### 4. Press Change, and try a failed save (about 3 minutes)

On that row press **Change**. The saved text and the button swap for an empty
box. Leave it empty and save, and the key stays: the ending hasn't changed. Now
press **Change** again, paste a different key, and save. The ending changes to
the new key's last four characters. If you edit only the models or temperature,
the key stays. If you change the row's provider in the dropdown, the key doesn't
follow it, and the save stops with "needs an API key" until you paste one. The
**x** at the end of a row removes it and its key.

Then try a failed save. Type a base URL like `ftp://example.com` in a row, type
something in a key box, and save. The page says what's wrong, followed by
"Nothing was saved. Keys are never shown again, so type any key you changed once
more." The key box comes back empty. "Even a failed save never puts a key back on
the page." Clear the bad base URL and save again so the table is clean.

### 5. Switch the default and watch the warning (about 3 minutes)

Set **Default chat AI provider** to a provider that has no row, for instance
xAI, and save. On the next admin page there's a warning, and which one depends on
what's saved. If the key saved before looks like another vendor's, it says "The
saved key looks like a gemini key, but the default provider is xai" (or whichever
two you have). If no key is saved anywhere, it says that xai is the default
provider but no key is saved for it. Either way it ends by telling you to add a
key for that provider in **Providers and keys** "before students use chat."

"The dropdown only picks a row. It never moved a key." Now add a row for that
provider with its key and save. The warning is gone, and chat uses that row's
key. (If you give that row a base URL of its own that differs from **API Base
URL**, you get a different warning instead: chat still uses the previous default
key until the two match or you clear the row's base URL.) Then set the default back to what it was and save. While you're here, type
`GPT-4o-mini` into **Model Name** with OpenAI as the default and save: the next
page warns that model ids are lowercase and suggests `gpt-4o-mini`. Put the real
model back.

### 6. Point Embedding at a row (about 3 minutes)

Open **Content and retrieval**. Above **Embedding API Key** there's a new
**Embedding key source** select. It offers "Use the key pasted below" and one
"Use the key from the ... row" for each provider with a saved key. Choose the
OpenAI row (or whichever matches your embedding provider) and save. Open **RAG
Index Status & Reindex**. The first status line shows your embedding provider
and "API key set." You didn't paste anything new.

One catch: a row with a base URL of its own is used only when it's exactly the
base URL Embedding sends to, so an Azure or gateway row is never sent to the
vendor's default endpoint. When the URLs differ, Embedding quietly uses the
pasted key instead, so if you expected the row's key, check the row's base URL.

"Same idea on two other pages." **Reranking** has **Rerank key source**, where a
`voyage` row is the usual choice, and **Engagement** has **Voice and TTS key
source**, which offers OpenAI rows only. A heads-up on that last one: choosing a
row there is what turns on the speak button, the Conversation Practice chip and
the speech-to-text fallback. Adding an OpenAI row for failover alone never does.

### 7. Confirm the page source holds no key (about 2 minutes)

Go back to **AI provider and models**. View the page source (Ctrl+U, or
Cmd+Option+U on a Mac) and search for the first characters of your key, such as
`sk-` or `AIza`, and for the ending you saw in "Saved, ends in". The only hit for
the ending is that visible text. Search for `type="password"`: every password
box has an empty `value`, and each saved row has one hidden field holding a short
row id, which is a keyed hash and not your key. "There's nothing in here to copy,
even for someone with the page open." Do the same on **Engagement** for the
Voice providers table.

### 8. Check the log and run the audit tool (about 2 minutes)

Open **Site administration, Reports, Config changes** and find the saves you
just made. Keys show as `********`. Rows from before 7.9.0 may still hold old
values, so from a shell on the server run:

```bash
sudo -u www-data php local/ai_course_assistant/admin/cli/audit_config_log_secrets.php
```

It lists any row where a key, a webhook URL, any other secret this plugin lists
or a table key sits in the log (for every plugin on the site, not only this
one), and prints no values. It exits with
1 if it finds any. `--redact` overwrites them, and `--ids=` does only the rows you
name. A table row loses only its key column. Redacting isn't rotating, so treat a
listed key as disclosed. The tool skips `#` comment lines and base URL columns,
so check those by hand.
