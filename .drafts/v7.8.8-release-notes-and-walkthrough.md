# SOLA v7.8.8: Release Notes and Walkthrough

## Part 1: Release Notes (14 October 2026)

## v7.8.8 (14 October 2026): backups are checked and failures explain themselves

This release came out of two incidents on a production site. A backup model was written as a display name (GPT-4o-mini) instead of its id, and every failover that reached it failed for days while the admin LLM picker still worked. A stale per-course key blocked 15 courses at once. In both cases the audit log said only "something went wrong".

**Backups are checked.** A daily task, a command-line check (`php local/ai_course_assistant/admin/cli/verify_failover.php`, add `--settings-only` to skip the requests) and the settings page now look at every chat backup provider. Settings problems need no network: a failover chain line with no row or no key, per-call failover on with no backup, a model written with capitals or spaces. The daily task and the command send one tiny real request per backup, built by the same code a failover uses, so the model goes out exactly as typed. Results show under Reports > Status, and a settings problem shows as a notice right after you save. Two failed checks in a row is an error.

**Failures explain themselves.** The failover rows in the audit log now carry what the provider actually said, with credentials removed and the length capped. If a provider refuses a long or malformed conversation (an HTTP 400, 413 or 422), SOLA asks again with the conversation repaired (no empty turns, same-role turns joined, first turn from the learner), then with only the newest exchange. Each attempt is logged. The variant that worked is remembered for that learner, in that course, for five minutes, and only for chat. Claude's request repairs a malformed history itself.

**One course can't block the others.** A provider's pause is now keyed to the key and model that failed, not just the provider's name. A request the provider calls malformed never pauses it. A rejected key, an unknown model or a billing or key problem pauses it at once for that key and model. Rate limits, outages and timeouts pause it on the second failure in a row inside a minute. A course that saved one provider's key and then switched to another provider is caught when its settings are saved (the key is refused or removed, with a notice) and listed under Reports > Status if it already happened. A course with its own base URL is never checked.

**Alerts that were silent now fire.** The unanswered-question alert counted a failed reply as an answer, so a provider that failed every call looked 100% answered. Failed replies now count separately. A new setting, "Failed replies that raise the alert" (default 3 in the window, 0 turns it off), also sends the alert when that many replies fail anywhere on the site, and the email names the most common provider message. The alert is still off by default. A chat stopped on purpose (the emergency pause) or refused by a limit before any provider was reached is stored as blocked and is not counted as a failure.

**Read-only audit access.** The new permission `local/ai_course_assistant:viewaudit` lets a monitoring account read the audit log without having moodle/site:config, which also allows changing every setting. No role has it by default, and it has no menu link, so the account needs the page address (`/local/ai_course_assistant/audit_log.php`). Site administrators can still open the page as before.

**Known limits.** A spend cap that runs out with no failover configured reads as answered in the unanswered-question alert, because learners are shown a notice; the 80, 95 and 100 percent spend emails cover that case. The new admin strings are translated into all 45 languages, and the less widely spoken ones would benefit from a native-speaker review.

Plugin version `2026101402`, release `7.8.8`.

## Part 2: Walkthrough (about 5 minutes (admin))

1. Open Reports > Status and find "AI Course Assistant backup providers" and "AI Course Assistant course keys".
2. Run `php local/ai_course_assistant/admin/cli/verify_failover.php --settings-only`, then run it again without the flag. The second run sends one tiny real request to each chat backup, built the same way a real failover is built.
3. In the plugin settings, add a failover chain line that has no matching Comparison providers row and save. A notice after saving names the problem. Remove the line again.
4. Open `/local/ai_course_assistant/audit_log.php`. Failover rows now carry `detail`, the provider's own words with credentials removed.
5. Find the unanswered-question alert settings (off by default), including "Failed replies that raise the alert".
6. Grant `local/ai_course_assistant:viewaudit` to a test role at the system level. An account with it opens the audit log without `moodle/site:config`.
