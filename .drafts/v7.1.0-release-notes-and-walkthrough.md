# SOLA v7.1.0 — Release Notes, Feature Summary, and 20-minute Admin Walkthrough

## Part 1: Release Notes (25 August 2026)

### The headline: no AI during Moodle quizzes

Learners can no longer use the assistant while they have a Moodle quiz attempt in
progress. On by default, on every quiz, on every surface -- chat, voice,
flashcards, practice quizzes. This is the release's reason to exist; everything
else below came out of the same investigation.

**The old lock did not work, and would not have held if it had.** Three separate
defects:

1. It never ran. The branch that reads a quiz's assistance level is gated on
   `!empty($PAGE->cm)`, which is always true -- `moodle_page` serves `cm` through
   `__get()` and defines no `__isset()`, so `isset()` and `empty()` report the
   property unset whatever it holds. `get_assistance_level()` had never been
   called in production.
2. It was never enforced on the server. `sse.php` only ever distinguished *coach*
   from *full*; there was no refusal for *hidden*. A comment there claimed the
   level was "enforced widget-side at injection time", which was not true of the
   code -- `$quizlocked` only set a data attribute, and the actual enforcement was
   `handleSend()` returning early in the browser.
3. It keyed off a course-module id **the browser supplied**. Even working and
   enforced, a learner could open the course home page in a second tab and have
   the assistant in full, with the exam open in the first.

v7.1.0 replaces the page-based check with a server-side one: does this learner
have a live quiz attempt? That is asked of the database, so it holds regardless of
which page the request claims to come from, and it is enforced at the provider
chokepoint rather than in one endpoint, so it covers every surface at once.

**Freshness is the part that needed care.** On learn.saylor.org ~88,900 attempts
sit in state `inprogress`, 95% of them started more than a month ago: self-paced
courses mostly set no time limit, and nothing transitions an abandoned attempt.
Treating any in-progress attempt as "sitting an exam" would have locked the
assistant permanently for 71,381 learners. Only ~66 attempts are under an hour
old, which is the population this is actually about. So an attempt counts while it
is inside its own time limit where it has one, and inside a configurable window
(default 180 minutes) where it does not.

**Any Moodle quiz now locks by default, not just graded ones.** The previous rule
-- lock when `grade > 0` -- matched 3,074 of 3,142 quizzes on Learn, so the
distinction bought almost nothing, and it had never been exercised. A teacher opts
an individual quiz out by setting its assistance level to *Full help*.

### Two fixes that came out of reading actual conversations

A third of SOLA learners send one message and never return. That holds on both
production sites — 1,181 of 3,446 learners on Learn, 125 of 367 on Degrees, within
0.2 points of each other. We read 50 of those conversations to find out why, and
the reasons were not the ones we had been guessing at.

Zero of the 50 contained a wrong answer. Zero showed retrieval coming up empty and
the assistant deflecting — across the whole window that pattern appears in 0.36% of
replies on Learn and 0.46% on Degrees. What we found instead was our own copy.

#### Quiz generation was billing us silently

`generate_quiz` made a real provider call and stored nothing. `spend_guard` totals
`prompt_tokens` and `completion_tokens` over the message table, so quiz spend
counted for nothing: it never contributed toward a cap, never reached token
analytics, and is absent from every cost figure we have published — including the
per-MAU projections.

The asymmetry is the part that mattered. Quiz calls were *subject* to the cap,
because the provider factory consults `spend_guard` before returning a client, but
*invisible* to it — so they could never help trigger the 80% and 95% notification
emails they were quietly pushing us toward.

Each generation now writes one telemetry row: `role='system'`, so
`get_messages()` keeps it out of the learner's visible history and out of the
model's context; `interaction_type='quiz'`; and a short marker rather than the
quiz JSON. It is a direct insert rather than an `add_message()` call, because
`add_message()` nulls `model_name` on any row that is not `role='assistant'` and
`spend_guard` prices by model — a row without one is counted but cannot be
costed. The embedding and rerank writers already worked this way.

Writing the row was necessary but not sufficient, and the first version of this
change stopped there. Billable rows are gated by
`analytics::spend_rows_predicate()` before `capability_sql('chat')` is ANDed on,
and that predicate matched only `role='assistant'` plus the embedding and rerank
types — so a `role='system'` quiz row was rejected before the capability clause
could ever see it. `'quiz'` is now named in the predicate too. This is the third
instance of the same shape in this codebase: the predicate exists because RAG
spend read $0.00 for exactly this reason.

**Found while fixing it: the non-streaming path discarded usage entirely.**
`last_token_usage` was only ever populated by `chat_completion_stream()`. Every
non-streaming caller — quiz generation, the mastery classifier, digests, essay
scoring — reported no tokens at all. The non-streaming API response carries the
same `usage` object; it was simply being thrown away. Now captured, which makes
those callers costable too.

#### "Study Plan" opened by asking the learner two questions

The chip's prompt told the assistant to ask what the learner wanted to accomplish
and how much time they had, before doing anything else. It worked exactly as
written. The learner then had to compose a substantive reply to get any value.

Learners who opened with that chip bounced at 43.9%, against 24.2% for learners who
typed their own question. Degrees replicates it: 41.7% against 25.8%. Somebody
clicked a button because they did not want to type, and was asked to type twice.

The chip now proposes a concrete first step and a realistic 30-minute sequence from
where the learner is in the course, and asks afterward whether to adjust. Existing
installs are migrated only where the prompt is still the superseded default, so an
admin who wrote their own copy keeps it.

#### "Explain This Page" no longer offers to explain the course catalog

Its prompt interpolates `{page}`. On an activity page that is a real topic, and the
chip is the strongest thing in the sample: 4 of 5 sampled replies cited course
material. On the course home page `{page}` expands to the entire course name and
the answer is a catalog blurb — 2 of 13 cited anything at all.

A new `activity` conditional suppresses the chip where there is no page, so the
button's name stops being a promise it cannot keep. The new parameter defaults to
permissive, so any caller that cannot determine page context keeps the previous
behavior rather than silently losing a chip.

#### Three checks in hook_callbacks had never fired

Found while wiring the fix above, and much larger than it.

`moodle_page` serves `cm`, `title` and `pagetype` through `__get()` and defines no
`__isset()`. PHP therefore answers `isset()` and `empty()` on those properties from
`__isset()` — which does not exist — so **`empty($PAGE->cm)` is always true, whatever
the property holds.** `??` is unaffected, which is why `$PAGE->pagetype ?? ''` was
never broken and this went unnoticed. Four checks in `hook_callbacks.php` used the
broken form: the one this release added, and three that shipped long before it.

**Per-quiz assistance level was inert.** Setting a quiz to *hidden* or *coach* had
no effect: the branch that reads the setting is gated on `!empty($PAGE->cm)`, so
`quiz_config_manager::get_assistance_level()` was never called and neither
`$quizlocked` nor `$quizcoachmode` was ever set. An integrity control that the
interface offered and the code ignored.

**Page-content grounding was inert.** `$currentpageid` stayed 0 on every page, so
`chat.js` never sent `pageid` at all (`if (currentPageId)` guards the assignment),
so `sse.php` never page-scoped retrieval and `context_builder` never injected the
current activity's content. The learner-visible symptom was masked, because the
page *title* falls back client-side to `data-server-page-title` — which works,
since it is built with `??`.

That last one revises a conclusion in the single-turn study. The study attributed
"Explain This Page" producing generic answers to `{page}` expanding to the course
name on the course home page. True, but not the whole cause: the page's content was
never reaching the prompt on *any* page. The five sampled activity-page answers that
did cite course material got that from RAG retrieval, not from page content. So the
chip was broken twice, and this is the half that mattered more.

### What this release deliberately does not fix

**9.5% of conversations contain a turn where the learner asked and no reply was
stored.** 112 of the 1,181 bounced learners on Learn never received a single stored
reply. We are not fixing it here because we cannot yet tell what it is: `sse.php`
saves the learner's message before calling the model and the reply only after the
stream finishes, and the plugin never calls `ignore_user_abort()`. A provider error
and a learner closing the tab mid-answer produce byte-identical evidence. The fix
is instrumentation first — persist a partial or error row — and that is the next
release, not this one.

**The Quiz Me chip still has no click instrumentation.** It is `type: quiz` and
opens a panel instead of sending a message, so we can now see what quiz generation
*costs* but still not how often the chip is *pressed* versus abandoned.

### Upgrade notes

- **One upgrade step, config only. No schema change.** It rewrites the saved
  `custom_starters` value: the study-plan prompt where it still matches the old
  default, and `conditional='activity'` on `help-page` where that field is empty.
  Sites that never customized starters have no stored value and simply pick up the
  new defaults.
- **Expect quiz spend to appear for the first time, as its own category.** Quiz
  is now reported separately rather than folded into chat: it stays inside the
  `chat` *capability* so the same cap applies to it, but it gets its own line in
  token analytics, because folding it into chat is what hid it. Chat totals will
  drop by the amount that is now attributed to quiz. Nothing is retroactive —
  no quiz row has ever been written, so historical figures do not move. The same
  applies to any non-streaming caller, which previously reported no tokens.
- **The assistant becomes unavailable during every Moodle quiz.** This is on by
  default and applies to all 3,142 quizzes on Learn and 561 on Degrees, graded or
  not. If you want it off, untick *Lock the assistant during Moodle quizzes*; if
  you want it off for one quiz only, set that quiz's assistance level to *Full
  help* in the course settings. Nothing here is retroactive and no learner data
  changes.
- **A learner with an abandoned attempt is not locked out.** Attempts are bounded
  by their own time limit, or by *Attempt freshness window* (default 180 minutes)
  where the quiz has none. This matters more than it sounds: 95% of the
  in-progress attempts on Learn are over a month old.
- **Prompts will grow, and get more specific.** The current activity's content and
  page-scoped retrieval now actually reach the model. Expect prompt token counts per
  chat turn to rise on activity pages. The read is gated by the v7.0.5 course-pin
  and visibility checks, so it cannot reach an activity the learner may not see.
- **Do not fund reranking on the strength of the bounce problem.** The hypothesis
  that bounces come from empty retrieval is refuted on both sites.

### Testing

- Full plugin PHPUnit suite green; validator suite 36 passed, 0 failed; PHP lint
  clean on every modified file; all 46 language files parse.
- Eight new tests cover both fixes. Two real defects were caught before merge,
  both of them the same shape as the bug being fixed:
  - The quiz row was first written through `add_message()`, which nulled its
    model name, leaving it counted but unpriceable. Found by a unit test.
  - The row was then excluded by `analytics::spend_rows_predicate()`, so the fix
    was inert and the spend total never moved. Found in review, **not** by the
    test — the test asserted only that the string `'quiz'` appeared in
    `capability_sql('chat')`, which proved nothing about the assembled query.
    It now writes a row and asserts the billable total moves by exactly the
    token count, and that assertion was confirmed to fail against the unfixed
    predicate before being relied on.
- No AMD rebuild: the changes are server-side, and starter filtering already
  happened in PHP.

Plugin version `2026082501`, release `7.1.0`.

## Part 3: Admin Walkthrough

Core drawer, quiz, voice, analytics, privacy, Soapbox and WSCUC-outcomes flows carry
forward from v7.0.5. Three things are worth fifteen minutes after this upgrade.

### Look at the new quiz line in token analytics

Site administration → Plugins → Local plugins → AI Course Assistant → Token
analytics. There should now be a `quiz` category. Whatever number is there has been
true for months; this is the first release that shows it. If you run per-course
spend caps, re-check your headroom against the new total rather than the old one.

### Press Study Plan as a learner, on a course you know

Open the assistant in a course and click Study Plan. You should get a proposed plan
naming real activities, followed by a single question about whether to adjust it.
If you instead get two questions and no plan, the upgrade step decided your site had
customized copy and left it alone — check the prompt under Conversation Starters and
update it by hand if that was not deliberate.

### Confirm "Explain This Page" is gone from the course home page

Open a course landing page: the chip should not be offered. Open any activity inside
that course: it should be. That is the whole change. If it is missing in both
places, something is passing the new page-context flag as false — the flag defaults
to true, so that would mean a custom caller is overriding it.
